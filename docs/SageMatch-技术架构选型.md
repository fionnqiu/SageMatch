## 1. 本次选型的判断依据

架构不由"什么技术流行"决定，而由 PRD 里的硬指标决定。从 PRD 提炼出 7 个架构驱动因素（D = Driver），后续每个选型都必须能回答"它服务于哪个 D"：

| 编号 | 驱动因素 | PRD 出处 | 架构含义 |
|---|---|---|---|
| **D1** | 多供应商接入（两类协议），切换后上层无感 | FR-A-01 ~ FR-A-04 | 必须自建协议适配层；业务代码不得感知供应商 |
| **D2** | 知识库全链路：解析 → 切分 → 入库 → 检索 → 可对比调参 | FR-A-05 ~ FR-A-12 | 需要一个同时管业务元数据与向量的存储，且删物料要立即生效 |
| **D3** | 出题质量四项硬指标 + 端到端 ≤ 2 分钟 | FR-U-03 ~ U-06、6.1、NFR-01 | 必须维度级并行；覆盖度与去重需要专门算法环节 |
| **D4** | 60 分钟长会话、跨 20 分钟准确引用历史 | FR-U-16、U-17、6.3、NFR-03 | 不能用"全量上下文硬塞"策略，需要结构化状态 |
| **D5** | 播报 ≤ 1s 启动、作答后 ≤ 1.5s 响应、可打断、可降级 | FR-U-12 ~ U-15、NFR-02、NFR-12 | 全链路必须流式；面试状态机必须与音频通道解耦 |
| **D6** | 评分可复现（σ ≤ 0.5） | FR-U-23、6.2 | 评分需要拆解为确定性流程，而非单次模型打分 |
| **D7** | 管理端可做召回/出题/评分三类质量评测 | FR-A-12 ~ A-14 | 所有 LLM 调用必须有统一埋点，否则指标无法计算 |

**一句话结论**：这是一个"**LLM 编排 + 混合检索 + 实时语音流**"的应用，架构重心在**编排层的流式与状态管理**，而不在后端框架本身。因此选型时对框架的"功能丰富度"不敏感，对"流式/并发/可观测"敏感。

## 3. 总体架构

采用**四层结构**，分层依据是"变更频率"与"供应商耦合度"：越往下越稳定，越往上越常改。

```
┌──────────────────────────────────────────────────────────┐
│  ① 表现层  React (Vite)                                    │
│    会话界面（岗位提交·维度展示·出题进度→发起面试）           │
│    模拟面试界面（题目卡片逐题浮现·多轮问答·复盘报告）         │
│    管理端                                                  │
└───────────────┬──────────────────────────┬───────────────┘
                │ SSE（文字、进度）          │ WebSocket（音频流）
┌───────────────▼──────────────────────────▼───────────────┐
│  ② 应用层  FastAPI                                        │
│  ┌──────────┬──────────┬──────────┬──────────┬─────────┐ │
│  │ 出题编排  │ 面试编排  │ 复盘评分  │ 知识库   │ 管理端   │ │
│  │ Pipeline │ Interview│ Scoring  │ RAG      │ Console │ │
│  └──────────┴──────────┴──────────┴──────────┴─────────┘ │
│  横切：TaskRunner · 进度推送 · 审计留痕 · 配置热读          │
└───────────────┬──────────────────────────┬───────────────┘
                │                          │
┌───────────────▼──────────────┐ ┌─────────▼───────────────┐
│  ③ 能力层                     │ │  ④ 存储层                │
│  LLMGateway  → 2 类协议适配器 │ │  PostgreSQL 16          │
│  EmbeddingGateway            │ │   ├─ 业务表 + JSONB      │
│  RAGEngine   → 混合检索+融合  │ │   ├─ pgvector (HNSW)    │
│  ASRGateway  → 流式转写      │ │   └─ tsvector (BM25)    │
│  TTSGateway  → 流式合成      │ │  本地磁盘 /data/audio    │
│  能力协商 / 重试 / 限流 / 埋点 │ │  Fernet 加密的密钥表     │
└──────────────────────────────┘ └─────────────────────────┘
```

> ★ **用户端只有两个界面（v2.2，随 PRD v1.7）**：① **会话界面**——提交岗位描述、看到系统识别出的考察维度（**只读告知，无可编辑表单**）、看出题进度、发起模拟面试；② **模拟面试界面**——题目随面试官提问**逐题以卡片浮现**、多轮问答、复盘报告。**不存在第三个用户端功能页面**：无题目集浏览页、无维度确认页、无成长趋势图表页。后端能力与页面数量无关——出题编排链路、`question_sets` / `questions` 表全部照旧（它们服务的是**面试提问**与**管理端评测**两个消费方）。

> ★ **认证口径（v2.3 新增，随待决策清单 A9 / N1）**：**管理端加固定管理员口令保护（可选叠加 IP 白名单），用户端匿名可用**。因此：① 架构图上「管理端」是一个**口令保护**的入口，用户端两界面**无需登录**；② 首版**不建用户表、不做登录注册**；③ `user_id` 沿用 §4.7 的"跑通阶段写固定值"；④ 管理端操作者身份由口令态标识，落 `audit_logs.operator`；⑤ **对外提供服务前须升级为真实鉴权**（见 §8「上线前置事项」第 5 项）。

**关键设计约束**：业务层（②）只能通过 ③ 的 Gateway 接口访问模型/语音能力，**禁止 import 任何供应商 SDK**。这是 D1「切换供应商上层无感」唯一可靠的实现方式——靠约定不如靠目录边界与 lint 规则。

**Agent 运行时属于应用层（②）内部**，它自身是**五层架构**：感知层 → 认知层（决策层）→ 记忆层 → 行动层 → 协调/编排层。各层职责、7 个角色（3 个自主 Agent + 4 个 LLM 确定性模块）、模块归属与层间边界规则见配套文档《SageMatch Agent 架构设计》§2 —— 本文档只在 §4.1 / §4.2 / §4.4 / §4.6 记录与选型直接相关的结论。

## 4. 关键模块选型论证

### 4.1 模型接入层（服务 D1）

这是本项目的架构核心，也是"看起来简单、做起来有坑"的地方。

**内部统一协议**：以 OpenAI Chat Completions 的结构作为内部规范（canonical），因为它最通用、且带完整的 tool calling 语义。适配器负责双向翻译。

| 适配器 | 目标端点 | 必须处理的真实差异 |
|---|---|---|
| `OpenAIChatAdapter` | `/v1/chat/completions` | 基准，无额外翻译。同时覆盖所有宣称 OpenAI 兼容的第三方服务（国内主流厂商、各类中转服务） |
| `AnthropicAdapter` | `/v1/messages` | system 是独立字段非 message；tool schema 字段名不同；`tool_result` 必须回传为 user role 的 content block；`max_tokens` 为必填；流式事件类型体系不同 |

**本期不支持 OpenAI Responses 协议**（决策调整）：

- **理由**：Responses 与 Chat Completions 结构不通用，需要独立适配（`input`/`output` item 结构、`instructions` 独立字段、reasoning item、`previous_response_id` 会话串联）。而它能覆盖的供应商范围**已被 Chat Completions 完全包含**——Chat Completions 是目前事实上的兼容标准，国内厂商与各类中转服务基本都提供。多维护一套协议翻译层的收益不足以支撑其成本。
- **代价一**：若某供应商只暴露 Responses 端点（少见），本期不支持，需改用兼容网关转发或换供应商。
- **代价二**：失去服务端会话串联（`previous_response_id`）。但本项目本就自管面试状态（结构化纪要 + `interview_turns`），不依赖供应商侧会话，**无实际损失**。

**结构化输出策略**（跨供应商一致性关键）：
1. **首选 tool/function calling 强制 schema** —— 两类协议都支持，一致性最好；
2. 不支持 tool 的供应商 → `response_format: json_object` + Pydantic 校验；
3. 校验失败 → 把 `ValidationError` 回灌给模型要求修复，最多重试 2 次。

统一入口：`gateway.structured_call(schema: type[BaseModel], messages, ...) -> BaseModel`。业务层拿到的永远是已校验的 Pydantic 对象。

**能力协商（Capability Negotiation）**：每个供应商在配置中声明能力矩阵（是否支持流式 / tool / 结构化输出 / 视觉 / 多模态），Gateway 在路由前检查，不支持则自动降级到备选策略而非直接报错。这直接服务 NFR-10（不得静默失败）与 NFR-11（重试不产生重复内容——重试用幂等键）。

**供应商健康度反馈路由**：每个供应商（LLM / ASR / TTS）维护滑动窗口运行时统计，路由时按健康度加权选择，自动避开劣化节点：

```
success_rate · p50/p95 latency · 熔断状态 · 连续失败数
   ↓  health_score = success_rate × w1 + latency_score × w2 × (1 − penalty)
LLMGateway / ASRGateway / TTSGateway 的供应商选择
```

这对 SageMatch 特别关键：**NFR-02 的 1.5s 硬指标直接由 ASR/TTS 首包延迟决定**。某 TTS 供应商首包从 300ms 劣化到 900ms 时，系统应自动切换，而不是等人工发现。注意健康度必须**持久化到 `provider_health` 表**而非进程内存——否则多 worker 下每个进程各算一份、互相不可见。

**Embedding 的特殊性**：embedding 与 LLM 是**两个不同的模型、两套独立配置**——前者把文本转成向量供检索，后者负责推理生成。它们既不是同一个供应商设置，调用方式也不同（embedding 是批量文本进、向量出，无流式、无 tool calling），所以不共用配置，也不参与"随手切换"。

这里要区分两个性质完全不同的问题：

| 轴 | 问题 | 状态 |
|---|---|---|
| **轴 1 · 向量维度** | 表结构写 `vector(N)` 的 N 是多少 | **不可逆 —— 已锁定 1024** |
| **轴 2 · 运行位置** | 本地跑还是调云 API | **已定：云 API**（见下） |

**运行位置为什么固定为云**：这是**项目级约束**（2026-09-21 决策）——全部模型能力走云 API，不自建推理。它不只是偏好，而是目标服务器的硬约束：`bge-m3` 约 2.3 GB，**2 GiB 内存装不下（会 OOM）**。完整论证见 §8「部署环境与资源约束」。

**但"维度不可逆"这条判断依然成立，且有个实际用途**：更换**云端供应商**（如从 A 家的 1024 维模型换到 B 家）只需重跑物料入库，**不动表结构**。只要候选模型都输出 1024 维，换供应商的成本就是可控的。

因此：
- 向量列维度**写死 `vector(1024)`** —— 这是真正的不可逆项，先定死；
- **运行位置：云 API，1024 维**（不采用 3072 维方案——维度翻三倍推高存储与检索成本，且会把维度绑死在少数供应商上，丧失换供应商不动表的余地）；
- 每条 chunk 记录 `embedding_model_version`，为供应商识别与迁移留下依据；
- embedding provider 独立于 LLM provider 配置。

> **全云路线的两个代价与应对**
> ① **云厂可能静默升级模型**，导致同一份文档在不同时间入库得到不同向量。应对：落 `embedding_model_version` + 调用时间戳；因维度已锁定，全量重嵌入的成本可控（只需重跑物料入库，不动表）。
> ② **物料入库受 RPM/TPM 限流**。应对：入库任务分批 + 退避重试。
>
> 这也解释了为什么 §4.1 必须建 Gateway 层：**全云意味着供应商单点依赖被放大，健康度路由、熔断与降级从"可选优化"变成"必需项"**（见上文供应商健康度反馈路由与 NFR-10/11）。

### 4.2 RAG 链路（服务 D2 / D3）

**存储选型：pgvector 而非独立向量库**

| 维度 | pgvector | Milvus / Qdrant | Chroma |
|---|---|---|---|
| 与业务库一致性 | 同事务，删物料即时生效 | 需跨系统同步删除 | 需跨系统同步 |
| 额外运维 | 0（同一实例） | 独立服务 | 0 |
| 混合检索 | 向量 + tsvector 同 SQL 内融合 | 内置更强 | 弱 |
| 规模上限 | 十万~百万级片段无压力 | 亿级 | 小规模 |

本项目知识库是管理员上传的技术文档，规模在千级到万级片段。**pgvector 是唯一不需要在"一致性"上额外付代价的方案**，而 FR-A-11（删除后立即不再参与检索）正是一致性问题。

**检索策略：三路召回 + RRF 融合**

```
query
 ├─ 路1  向量召回（原 query）              pgvector HNSW, cosine, top-15
 ├─ 路2  关键词召回（原 query）            tsvector BM25 + pg_trgm, top-15
 └─ 路3  改写子查询召回（N=3 个角度，向量） pgvector, top-10 each
        ↓  三路并行（asyncio.gather）
   RRF 融合 (Reciprocal Rank Fusion, k=60) + 内容哈希去重
        ↓
   （可选）Rerank → 最终 top-8 送 LLM
```

为什么必须做关键词召回：技术文档充满专有名词与缩写。纯向量检索在"Raft 选举超时"vs"Paxos 选举超时"这类查询上会明显漂移，而关键词召回能精确兜住。这直接影响 FR-U-02（检索质量 → 出题质量）。

为什么加改写子查询（来自 EchoMind 的 `search_with_rewrite`）：单一 query 只能召回一个语义角度。把考察维度改写为多角度检索式（如维度「熟悉分布式一致性协议」→ `["Raft 选举机制", "Paxos 与 Raft 区别", "分布式共识的容错边界"]`）能显著提升召回率与出题可用率。

**检索档位化 `retrieval_profile`（关键决策）**：参数按档位分离。**本期实际只启用 `offline` 一档**。**v2.5**：top-k / top-p / temperature / 分块大小 / 分块重叠**不在管理端热改**，后续写入后端 config 文件后再与实现一并处理（FR-A-05/06 后置）。

| 档位 | 起用路 | 改写 | 重排 | 延迟目标 | 用于 |
|---|---|---|---|---|---|
| `offline` | 路1 + 路2 + 路3 | ✅ LLM 改写 N=3 | 可开 | 秒级可接受 | 出题、召回测试、管理端评测、**面试前置准备** |
| `online` | 路1 + 路2 | ✗ | ✗ | ~300 ms | **本期无启用场景（预留）** |

> `online` 档之所以本期不用：它与配套文档《Agent 架构设计》§4.2「约束 B」的**在线 ReAct 工具执行预算 <50ms** 直接冲突（本档 ~300ms 超标）。更根本的原因是**面试官的职责是追问用户的回答，不是输出领域知识**——判断"要不要深挖某一点"的依据是用户回答里的含糊处（记忆层），而不是知识库。若让面试官查知识库来评判答案对错，实际上是在面试中做隐含评分，违反 FR-U-19 的立意。因此面试所需知识改为**面试开始前一次性预取**（`offline` 档）并缓存进面试记录（落 `interviews.prefetched_knowledge`，见 §4.7），面试中只读缓存。

管理端 FR-A-12 的召回测试可切换档位对比，**直接支撑 FR-A-07 的「可对比」要求**；返回结果需标注每段内容来自哪一路（向量命中 / 关键词命中 / 改写命中 / 融合后），否则无法解释调参效果。

**Rerank 决策**：本期**保留接口但默认关闭**。理由：重排能提升精度，但增加 200–500ms 延迟，而 NFR-01 的出题预算（120s）本就吃紧（见 §4.3）。Phase 3 可用小样本试跑做初步判断，最终**以 Phase 7 齐备的 FR-A-13 评测数据决定是否开启**（FR-A-13 的全量评测在 Phase 7「质量评测模块收口」齐备，见 §8）。

**配置权威源（v2.5 收口）**：top-k、top-p、temperature、分块大小、分块重叠**本期不进管理端、不写入 `app_settings` 热改**。后续放入后端独立 config 文件（`backend/config/rag.yaml`），与后端实现一并处理后再定义热加载方式。此前「`app_settings` 为唯一权威源」的口径**仅冻结、不在本期落地**，避免管理端与文件双源。

**召回测试（FR-A-07，v2.5）**：输入 Query 后查看**一路**命中片段与排序；**不在界面改参，不做 A/B 双方案**。

### 4.3 出题链路（服务 D3）—— 最难保障的是延迟

**NFR-01 是硬约束：8–15 个维度，端到端 ≤ 120 秒。** 这个预算意味着**串行多轮设计直接出局**。

```
岗位描述
  ↓
[①] 维度识别（感知层）    1 次 LLM 结构化输出 → 维度列表（技能方向 / 知识领域 / 经验要求）
  ↓                      ★ v2.2：识别结果**自动生效**，无用户确认环节
[②] 维度级并行检索        每维度 top-8 混合检索（行动层）
  ↓
[③] 维度级并行出题        每维度 1 次 LLM 调用 → 2~4 题（tool calling 强制 schema；并发 ≥8）
  ↓
[④] 去重 + 重复维度重出   题干 embedding 两两 cosine > 0.9 判重 → 命中即重出（限 2 次）
  ↓
[⑤] 质检                  覆盖度校验 + 跨维度去重 + 抽样盲测（每维度 1 题）
  ↓
[⑥] 覆盖度补生成          缺失维度补生成（限 1 轮）
  ↓
[⑦] 落库为「题目集」+ SSE 进度回传
```

> **★ 链路阶段数：8 → 7（v2.2，随 PRD v1.7 删除维度确认）**：原第 ② 步「用户确认 / 编辑维度」已随 FR-U-02 一并删除。维度识别结果**自动生效**——系统识别出什么就用什么出题，用户不审核、不编辑、不提供增删改入口。
>
> **连带影响**：① 链路变为**全程自动、无人工介入点**，NFR-01 的「≤2 分钟」由此成为**纯系统耗时**（原口径中"不计入人工停留"的豁免条款失效）；② 维度列表在**会话界面只读告知**（用户知道系统认为这个岗位要考什么），但它不构成一个交互环节；③ §4.3 的延迟预算表**数字不变**（该步本就不计入 120s）。

> **链路的性质与终点（v2.0 明确，v2.1 补用途唯一性，v2.2 精确化）**：本条链路的产出是**题目集**，它**只有两个用途**——① **面试提问的依据**（考察维度 → 具体问题的映射）；② **管理端出题质量评测（FR-A-13）的验证对象**（§5.1 四项指标的计算基础）。
>
> ★ **用途唯一性（v2.2 更新）**：**出题能力的唯一消费方是「模拟面试」与「管理端评测」**——不存在第三个消费方。经 PRD v1.7 的第二次收缩，**题目集"查看视图"这条出口也已取消**（原 v2.1 所述的"题目集页"已删除）：题目在用户端**只随面试官提问逐题以卡片形式出现在模拟面试界面**（PRD FR-U-11）。因此本链路的下游出口收敛为一个:**面试提问**（管理端评测是旁路出口，不面向用户）。
>
> **它不再有面向用户的作答出口，也没有集中的查看出口**：PRD v1.5 已删除答题板块（原 FR-U-10 ~ U-13），PRD v1.7 又删除了题目集浏览页面与维度确认环节。用户从提交岗位到题目就绪**全程无需任何操作**，就绪后**直接发起模拟面试**。因此本链路的终点是「题目集就绪 + 进度推送」，**不含作答、判定、作答历史、题目列表浏览**。①–⑦ 步全部保留且 §4.2 的延迟预算不变——**NFR-01 验收的是这条链路的系统耗时，与用户是否操作无关**。
>
> ⚠️ **不要因为"用户看不到题目"而删掉这条链路**：删除它会同时抽掉 §5.1 四项指标的测量对象与 FR-A-13 评测的业务参照（评测将退化为"自己出一套题、自己测自己"，失去意义）。**注意区分：可以删的是"作答交互"与"查看页面"，不是"出题能力"。** 出题链路在两次收缩后已完全变成**"看不见但必须在"的支撑层**。

**延迟预算估算（12 维度、并发度 ≥8）** —— 与配套文档《Agent 架构设计》§4.2 **同源同表**，两处数字必须一致：

| 阶段 | 耗时估算 | 备注 |
|---|---|---|
| ① 维度识别（感知层） | 10s | 单次调用（**识别结果自动生效，无人工确认**） |
| ② 并行混合检索（行动层） | 1s | 12 维度并发 |
| ③ 并行出题（认知层） | 40s | 12 维度 / 并发 ≥8 → 2 批 |
| ④ 去重 + 重复维度重出 | 20s | 约 20% 命中，并行；含题干 embedding 计算 |
| ⑤ 质检（覆盖度 + 跨维度去重 + **抽样**盲测） | 20s | 抽样 = 每维度 1 题（见 §4.3「干扰项」段） |
| ⑥ 覆盖度补生成 | 0–15s | 仅当有缺失维度时触发（限 1 轮） |
| ⑦ 落库 + SSE 进度推送 | < 1s | |
| **合计** | **91s（无补生成）/ ~106s（含补生成）** | ✅ 有余量 |

> **表内编号为 v2.2 的 7 阶段编号**（原 8 阶段中的「用户确认 / 编辑维度」已删除，该步本就不计入本表，故**各行数字完全不变**）。

**风险点**：**并发度是唯一的强敏感变量。** 12 维度并发 8 → 出题 2 批；若实测并发上限只能到 6，出题变 3 批（+20s），合计升至 ~111s（含补生成约 126s），**贴线甚至超标**。因此：

- **并发度 ≥8 是设计要求（下限）**，实测上限由云 API 的 RPM/TPM 决定（Phase 0 必须实测，见 §9 未决项 #3）；
- 若实测上限 <8，应先做三件事之一，而不是直接放弃 NFR-01：① 向供应商申请提高限流配额；② 降低单维度题量（2~4 题按 2 题出）；③ 把去重与质检进一步异步化（用户先看到已达标维度，补齐进度单独推送）；
- 出题任务必须**异步化 + SSE 进度推送**，前端展示"正在生成 7/12 维度"，用户不必盯着转圈；
- 任务状态落 PG，页面刷新可恢复。

**关于 FR-U-05「不重复」与 6.1「重复率 < 10%」**（PRD 已统一为**同一组数值**，见 PRD §6.1 口径说明；10% 是**验收上限而非目标值**，故本链路仍须执行两层去重）：
- 生成时：把同维度已生成的题干回灌进 prompt，让模型主动避让（省成本）；
- 生成后：题干 embedding 两两 cosine > 0.9 判重，命中则重生成（兜底，最多 2 次）；
- 两层都需要，因为仅靠 prompt 约束实测不可靠。

**关于 FR-U-06 / 6.1「干扰项有效性 20–50%」**：这是最反直觉的指标——既要迷惑性，又不能有歧义（低于 20% 说明无迷惑性，高于 50% 说明答案不明确）。技术手段：
- **Prompt 约束**：干扰项须为"看似成立但存在关键细节错误"的同类选项；禁止"以上都对/都不对"；**禁止选项长度明显偏离正确项**（选项长度是模型泄漏答案的最大特征）；
- **规则校验**：选项长度方差、选项间词面重叠度、绝对化措辞（"一定""永远"）检测；
- **盲测质检（FR-A-13 的核心实现）**：仅把题干 + 选项（**不给知识内容**）交给另一个模型作答，统计误选比例。这正是 6.1 指标的自动化实现方式，应作为独立评测环节。
  > ⚠️ **"不给知识内容"这一输入边界需业务确认**：不给知识测的是"仅凭常识能否排除干扰项"，给知识测的是"读懂知识后是否仍会误选"（更贴近真实迷惑性）。**6.1 的 20%–50% 区间在不同定义下含义完全不同**，故列为 §9 未决项 #9，须在 Phase 3 前确定。

### 4.4 模拟面试链路（服务 D4）—— 第二难点

**上下文策略：结构化面试状态（Interview State），而非全量上下文**

先澄清一个常见误判。60 分钟约 20 轮、每轮语音转写约 200 字，总对话约 1–2 万 token —— **现代 128k 上下文完全塞得下**。所以问题不是"塞不下"，而是：

1. **注意力衰减才是 NFR-03 的根因**。在一万多 token 的杂序对话中定位"20 分钟前那句关于 GC 的回答"，模型确实会漏。6.3 要求"重复提问/忘记前文 ≤ 1 次/场"，靠硬塞上下文达不到。
2. **延迟与成本不可控**：每轮全量重发，20 轮累计输入 20 万 token，成本线性增长；且长 prompt 会拉高首 token 延迟，直接侵蚀 NFR-02 的 1.5s 预算。
3. **轮次无上限**（FR-U-16），极端情况可能 40+ 轮。因此编排层需要一个**内部兜底轮次上限**（不对外暴露、不表述为"限制轮次"）：当轮次或时长超过安全阈值时，强制进入收尾流程，防止模型长时间不触发 `wrapup` 而耗尽资源。

因此采用三层上下文组装：

```
送给面试官的上下文 =
    系统提示（角色 + 当前考察维度 + 评分不在此处）
  + 结构化面试纪要（全量事实，JSON）
  + 最近 3~5 轮原文（保持语气与语境连贯）
  + 当前待问/待追问的主题
```

**结构化面试纪要（`interviews.state` JSONB）字段设计**：

```jsonc
{
  "covered_dimensions": [
    { "dimension_id": 3, "status": "covered", "depth": "shallow" }
  ],
  "asked_questions": [
    { "turn_id": 7, "dimension_id": 3, "question": "…", "intent": "验证并发模型理解" }
  ],
  "answer_points": [
    { "turn_id": 8, "quote": "我用了 channel 做同步…",
      "assessment": "缺少背压处理", "answer_mode": "voice" }
  ],
  "pending_probes": ["背压处理", "channel 缓冲区设计"]
}
```

每轮对话结束后**增量更新**（用低成本模型做摘要），而不是结束时一次性生成。之所以必须增量而非批量：一次批量压缩会留下一个窗口，窗口内的事实条目缺失，正是"忘记前文"的成因。增量更新不在用户等待的关键路径上，可与用户说话并行，开销可接受。这样 20 分钟前的语音作答内容会以"事实条目"存在，模型不需要"回忆"，只需"阅读"。

**「全量存储 + 选择性注入」——不丢原文**：原文全量持久化到 `interview_turns`（文字 / 语音路径 / 转写文本 / 作答方式），**永不删除**；只有送入上下文的组装过程是选择性的（结构化纪要 + 最近 3–5 轮）。需要引用任意历史轮时，用 `get_turn_quote(turn_id)` 按主键精确取回（<10ms）。

这是与"压缩丢弃式"上下文管理（把旧消息压缩成摘要后删除原文）的本质区别。SageMatch 不能丢原文，因为：
- FR-U-24 要求「查看完整历史与**对话回放**（含文字与语音作答内容）」
- FR-U-21 要求复盘指出「**第 4 轮**追问的回答过于笼统」——精确定位到轮次
- FR-U-17 要求面试官能准确引用 **20 分钟以上**的回答

用「结构化纪要压缩**事实层**」+「按需精确取原文」同时达到控制上下文长度与保留可引用性的目的。

> 相关设计细节见配套文档《SageMatch Agent 架构设计》：两层循环与 ReAct 预算在 §4.2（认知层）、记忆三层与全量存储在 §5（记忆层）、工具白名单在 §6.1（行动层）。

**引用溯源（服务 6.3「历史引用准确率 ≥ 95%」）**：
- 纪要每条带 `turn_id` 与原话片段；
- 要求面试官追问时以 `[[turn:8]]` 形式标注引用来源；
- 前端校验该 turn 是否真实存在（**防幻觉引用**），并记录校验失败率 —— 这就把"历史引用准确率"变成了可自动计算的指标，而非靠人工抽查。

**阈值驱动收尾（FR-U-18，v2.4 改写）**：**触发收尾的主条件是编排层的内部安全阈值**——轮次或时长达到阈值、或模型判断考察已充分时，允许主动收尾。`covered_dimensions` 与 `pending_probes` 降为**辅助参考**（作为 prompt 上下文的一部分供模型判断），**不再是唯一触发条件**。
>
> **为什么改**：v1.9 起维度降为内部机制、用户端不展示，若仍以“覆盖完毕”作为唯一收尾条件，收尾时机会被一个**用户完全看不见的内部状态**支配；而 FR-U-16 本就不设轮次上限，两者叠加会让面试时长不可预期。改为阈值驱动后，收尾行为**可预测、可验收**，且与 PRD FR-U-18 的新表述一致。

> ★ **取题机制：题集驱动 + 题内自由追问（v2.3 新增，H1）**：面试官**从题目集按顺序取题**为主线（保证 FR-U-11 的题目卡片总有内容、且与 FR-U-04 的覆盖率 ≥90% 天然自洽），在**同一道题内**可依用户回答自由多轮追问（FR-U-10 不受限）。**"下一题"的取得方式**：由**编排层按覆盖进度直接算好并注入上下文**（沿用 §4.2 约束 A 的"高频只读状态走上下文注入"思路），**不新增在线工具、不增在线 LLM 往返**，<50ms 预算不变。详见 Agent 文档 §7.1 形态二与 §4.2 约束 A。

**FR-U-19「不显示实时评分」的架构含义**：评分是**面试结束后的独立离线任务**，不在面试链路上。这同时让 D6 的评分一致性更容易做（可重复执行、可缓存）。

### 4.5 语音链路（服务 D5）

**整体形态：回合制 + 流式分段**

```
【面试官发言】
LLM 流式 token ──► 前端增量渲染文字（文字形态 ✅）
              └─► 后端按句边界切分（。！？\n，或首句最小字数 12 字）
                  └─► 逐句送流式 TTS ──► 音频分片经 WS 推送
                                        └─► 前端 AudioQueue 顺序播放（可随时 interrupt）

【用户作答】
点按/按住开始 ──► MediaRecorder(timeslice=200ms) 分片
              └─► WS 推后端 ──► 流式 ASR 边推边出中间结果
              └─► 浏览器 VAD 检测静音（600–800ms）自动结束，或用户手动结束
                  └─► 取累积文本（不等 ASR final）──► 写入面试上下文 ──► 触发下一轮
```

**延迟预算（NFR-02）**

作答后响应 ≤ 1.5s 的目标链路：

| 环节 | 优化手段 | 预估耗时 |
|---|---|---|
| 用户说完 | 浏览器 VAD 本地判停 | 属用户自然停顿，不计入 |
| 结束信号 → 文本就绪 | **不等 ASR final**，用已累积的流式中间结果 | ~0s |
| LLM 首 token | 低 temperature、prompt 精简、连接池预热 | 0.3–0.8s |
| 首句切分 + TTS 首包 | 遇首个句末标点即切；TTS 流式接口 + 连接预热 | 0.3–0.6s |
| **合计** | | **0.6–1.4s** ✅ 偏紧 |

播报启动 ≤ 1s 的目标链路：

| 环节 | 预估耗时 |
|---|---|
| LLM 首句文字到达 | 0.5–1.0s |
| TTS 首包到达 | 0.3–0.6s |
| **合计** | **0.8–1.6s** ⚠️ **有超标风险** |

**因此必须准备两处兜底，缺一不可**：

1. **过渡语预合成**：面试官的固定话术（"好的，我们开始"、"嗯，我接着问下一个问题"）预先生成音频并缓存。多数轮次里音频已经先播着过渡语，正式问题的文字同步出现，1s 指标自然满足。
2. **语气填充音（Filler）**：若首句 TTS 预估超过 1s，先播一个预合成的短语气音（"嗯……"），掩盖后端处理时间。这是真实语音产品的常用手法。

**打断（FR-U-15）的关键实现**：前端 `AudioQueue.stop()` 清空播放队列只是第一步 —— **必须同时把 `interrupt` 信号发给后端，取消正在跑的 LLM 流**（`asyncio.CancelledError`），否则后端会继续生成并推送音频，既浪费 token 又造成"打断了还在说"的错乱。

**浏览器音频兼容（v2.3 明确，F3）**：

| 事项 | 结论 | 理由 |
|---|---|---|
| **mimeType 能力协商** | ❌ **不做** | 该协商是 **Safari 专属**需求（其对 `audio/webm;codecs=opus` 支持不完整）。F3 已定案**只保 Chromium 系最新两个大版本**（PRD NFR-13），`MediaRecorder` 可直接指定 opus，无需运行时协商 |
| **`AudioContext` 解锁时机** | ✅ **必须做**（N5/G7） | **与浏览器选型无关**——Chromium 同样遵循自动播放策略：未经用户手势的 `AudioContext` 会停在 `suspended` 态，播报根本不出声、NFR-02 的 1s 指标直接崩。做法：在**首次用户手势**（点击「开始面试」）时同步调用 `audioContext.resume()`，并把该时机作为面试状态机启动的前置条件 |

**降级（NFR-12）的架构前提**：`AudioOutputManager` 监听 `AudioContext.state`、播放失败、无音频设备等信号，触发降级为纯文字。**硬性约束：面试状态机必须与音频通道完全解耦** —— 音频只是渲染层的一种输出通道，任何音频异常都不允许影响面试流程推进。这条如果做错，后面几乎无法补救。

**ASR / TTS 供应商选型**（候选**限定为国内可直连的服务**——目标服务器在深圳，境外服务不可用，见 §8 部署环境约束）

| 能力 | 候选 | 评估要点 |
|---|---|---|
| ASR（中文） | 火山引擎（豆包语音）、阿里云、腾讯云、讯飞 | **自定义热词表是必选项**（服务 NFR-04）；流式接口与首字延迟 |
| TTS（中文） | 火山引擎、阿里云、腾讯云 | 流式首包延迟（决定 1s 指标）；音色自然度；并发与成本 |

**关于 NFR-04「专有技术名词识别错误不得影响追问判断」的具体做法**：
1. **面试开始前**（与预取知识同批完成），从本次考察维度中抽取技术名词，**动态注入 ASR 热词表**（如 "Raft"、"背压"、"分代回收"），并落 `glossary_terms` 供后续复用；
2. 转写后做**术语纠正**：以 `glossary_terms` 表（字段与来源见 §4.7、§9 未决项 #8）为准，做编辑距离 / 同音字校正；
3. 低置信度片段标记，前端可提示用户确认。

风险表已明确"语音能力依赖外部服务 → 管理端支持多供应商切换"，因此 `ASRProvider` / `TTSProvider` 需与 LLM 供应商配置**共用同一套管理端与配置表**，只是 `capability_type` 不同。

### 4.6 评分与复盘（服务 D6）

**σ ≤ 0.5 不能靠 `temperature=0` 达成** —— 即使温度为 0，跨供应商、批处理、浮点累加都会带来抖动。正确做法是**把评分从"一次模型打分"改造成确定性流程**：

```
用户每轮回答
   ↓
[Step 1] 证据抽取（temperature=0，结构化输出）
   产出：优点 / 缺陷 / 支撑原话引用 —— 不含任何分数
   ↓
[Step 2] 维度打分（temperature=0，输入是 Step1 的结构化证据而非原始回答）
   rubric 含行为锚点：1-3 / 4-6 / 7-8 / 9-10 分别对应什么表现
   ↓
[Step 3] 加权合成（纯计算，零随机性）
   维度分 × 固定权重 → 整体分
   ↓
[Step 4] 生成复盘文本（可基于 Step1/2 的既有结论，不重新判断）
```

**Step 1–3 与 Step 4 分属两个角色**（详见配套文档 §4.6）：`ScorerAgent`（评分员，温度 0.0）负责到 Step 3 并在产出点**冻结分数**；`CoachAgent`（复盘教练，温度 0.3）只读冻结结果生成报告。理由：Step 4 是唯一一次"要写给用户看"的调用，若与 Step 2 同处一个角色，模型可能为让报告自洽而微调分数——即「叙事倒灌评分」。拆分后 `ScorerAgent` 的上下文里**不含"要写给用户看的文字"这个目标**，隔离是结构性的而非靠 prompt 约定。附带收益：分数冻结使复盘文案可独立重生成，文案迭代不必重跑评分。

**评分粒度（口径定义）**：评分以「**每场面试 × 每个考察维度**」为最小单元——Step 2 按维度并行，每个维度用独立上下文，输入是该维度下所有轮次的回答证据；整体分由各维度分加权合成（Step 3，纯计算，**不单独缓存**）。因此 PRD §6.2 中的"同一份回答"应理解为"同一场面试的回答集"。
>
> **v2.4 口径补充**：因 PRD FR-U-20 已取消分项得分，**对外的评分呈现只有整体分**；上述「按维度并行 + 加权合成」仍是**内部实现**（用户端不展示任何分项，包括维度分）。

**术语说明**：本文档早期称该流程为「**两步评分**」（指 Step 1 与 Step 2 两次 LLM 调用）。完整流程是**四步**——Step 1–3 归 `ScorerAgent`（两次 LLM 调用 + 一次纯计算），Step 4 复盘文本归 `CoachAgent`。本文档与配套文档统一使用「**评分四步**」这一表述。

四个稳定性来源：
1. **证据先行**：模型先看证据再看分，减少自由裁量；
2. **行为锚点**：把模糊的"好/差"变成可判定的行为描述；
3. **权重固定 + 计算合成**：整体分的随机性被压缩到维度分这一层；
4. **版本锁定 + 缓存**：`scoring_cache` 表以 `(answer_set_hash, dimension_id, provider_id, model, prompt_version, rubric_version)` 建唯一索引，同输入同版本直接命中缓存返回 —— 这天然保证"同一份回答集多次评分结果稳定"。

**必须记录 `prompt_version` 与 `rubric_version`**：否则一旦出现评分不一致，无法定位是模型换了还是标准改了。同时这也支撑 FR-A-14 的一致性评测 —— 跑 N=5 次算标准差，σ > 0.5 说明 rubric 描述有歧义，回炉改 rubric 而不是改模型。

**版本化热加载**：`rubrics/*.md`（含分数档行为锚点）、`prompts/*.md`、`retrieval_profiles.yaml` 三份资产支持运行时热加载（对应 FR-A-06 的即时生效与 FR-A-05 的参数可配）。其中 **`retrieval_profiles.yaml` 只提供出厂默认档位值**，运行时的生效参数一律读 `app_settings` 表（见 §4.2），避免"文件与库各有一套值"的双源问题。关键补充：**每次热加载时对文件内容取哈希作为版本号**，随 `llm_call_log` 与 `reports` 落库。

**评分与复盘的模型可分别选择**：`ScorerAgent` 可用更强更稳的模型以获得更好的 σ，`CoachAgent` 可用更快更便宜的模型（它是最长输出）。因此 `reports` 表**按两次调用分别记录版本字段**（`scorer_*` / `coach_*`，见 §4.7 与 §7 决策 2），而不是只留一组——否则"这次评分用的哪个模型"无法归因。

没有版本号的"热更新"是危险的 —— 配置改完立即生效，但历史评分记录再也无法解释自己是用哪版标准算出来的，"评分可复现"就失去了归因能力。版本号让"模型换了"和"标准改了"这两类原因可区分。

**`llm_call_log` 是隐形的关键表**：6.1 / 6.2 / 6.3 的每一项指标都要靠它计算，NFR-08 的留痕也要靠它。**必须在 Phase 1 就建好，不要等到做评测模块时才想起埋点** —— 那时历史数据已经缺失，无法回算。

**另外三条不可省的约定**：

- **`glossary_terms` 的来源**：由管理员维护，并支持从已入库物料自动抽取候选术语后人工确认（维护方式见 §9 未决项 #8）。

## 5. PRD 指标 → 技术实现映射

这张表是本文档的核心交付：**每个验收指标都必须能指向一个具体的实现机制**，否则指标只是愿望。

### 5.1 出题质量（6.1）

| 指标 | 目标 | 技术实现 |
|---|---|---|
| **出题覆盖度**（v2.4 改名） | ≥ 90% | 生成后做**维度集合比对**（内部机制）；缺失维度触发补生成（最多 1 轮，FR-U-04）；覆盖度结果写入**题目集**（`question_sets`）供**管理端评测**读取。**内部指标，用户端不展示** |
| 题目重复率 | < 10% | 生成时同维度题干回灌 prompt 避让 + 生成后题干 embedding cosine > 0.9 判重重生成（最多 2 次） |
| 干扰项有效性 | 20%–50% | ① prompt 约束（同类错误项、禁"以上都对"、禁长度差异）；② 规则校验（长度方差、词面重叠、绝对化措辞）；③ **盲测**：仅给题干+选项让独立模型作答，统计误选率（FR-A-13 核心） |
| 出题可用率 | ≥ 80% | 结构性自检 —— `validate_question` 承担**纯计算项**（答案唯一性、选项文案互不重复）；**语义项**（题干自足性、解析与答案一致性）由 `QuestionCriticAgent` 的 LLM 质检承担（两者分工见配套文档 §6.1）+ 人工抽检 |

> **口径**：本节四项指标（覆盖率 ≥90%、重复率 <10%、干扰项有效性 20–50%、可用率 ≥80%）即**验收线**，与 PRD 的 FR 使用**同一组数值**，不存在"目标值 / 验收线"两套标准（PRD §6.1 口径说明，2026-09-21 确认）。
>
> **★ 验证渠道（v2.0 明确，v2.2 复核仍成立）**：四项指标的测量对象是**题目集本身**，与用户是否作答无关、也与用户能否浏览题目无关。**答题板块删除（v2.0）与题目集页面删除（v2.2）后数值与达成机制均不变**，但验证渠道收窄：
>
> | 指标 | 渠道 |
> |---|---|
> | 覆盖率 / 重复率 | 出题链路内置工具（`check_coverage` / `check_duplicate`）+ **FR-A-13 评测复核** |
> | 干扰项有效性 / 可用率 | **仅 FR-A-13 管理端评测**（抽样或全量盲测 + 人工抽检） |
>
> 这也正是**出题链路不可随用户端页面一并删除**的技术原因：删掉它，本节四项指标将失去测量对象，FR-A-13 也会失去业务参照（配套文档 §7.5 明确"评测必须复用业务出题链路，否则评测合格无法推出业务合格"）。
>
> ★ **v2.2 强化说明**：经 PRD v1.7 的第二次收缩，**题目在用户端已无任何列表式展示出口**（只在面试中逐题浮现），本节四项指标的**唯一出口就是 FR-A-13**——用户侧已不存在任何"看到题目"的渠道。这不改变数值，但使 FR-A-13 从"重要验证手段"变为"**唯一验证手段**"，其采集的样本量与覆盖面必须有保障（见 §9 未决项 #9 的盲测输入边界）。

| 指标 | 目标 | 技术实现 |
|---|---|---|
| 历史引用准确率 | ≥ 95% | 结构化面试纪要（含 turn_id + 原话片段）+ 强制 `[[turn:N]]` 引用标记 + 前端校验引用真实存在 |

| 复盘可用率 | ≥ 80% | 复盘文本必须绑定 Step1 抽取的具体证据（含 `turn_id` 与原话），禁止自由发挥；prompt 强约束"问题须定位到具体轮次" |

| 指标 | 目标 | 技术实现 |

## 6. 被否决的方案与取舍说明

| 方案 | 否决原因 |
|---|---|
| **模型能力本地化自建**（本地 ASR / TTS / Embedding / LLM） | **目标服务器规格不允许**（2 vCPU / 2 GiB）：`bge-m3` 约 2.3 GB 装不下内存；中文可用的 ASR 模型在 2 核上实时率不达标；能达"面试官"音质的 TTS 方案需 1–4 GB 模型且 CPU 生成 10 秒音频要数十秒；7B 量化 LLM 要 4–5 GB。**这是"全云"成为项目级约束的根因**，详见 §8 |
| **SQLite** | 无向量检索生态，无法在同库内做混合检索；FR-A-11 的删除一致性也会更难处理 |
| **Milvus / Qdrant 独立向量库** | 本项目片段规模万级，独立向量库带来的跨系统一致性成本远大于其性能收益 |
| **Chroma** | 零运维但过滤与并发能力弱，且同样要处理与业务库的一致性 |
| **LangChain 全量引入** | 框架抽象层较厚，Anthropic 与 Chat Completions 的结构差异（system 独立字段、`tool_result` 回传形态、流式事件体系）会被框架"统一"掉，反而失去 FR-A-01 所需的控制力；调试链路黑盒化。**但可借鉴其 splitter 实现思路。** 若团队 LLM 工程经验较少，可少量用于非关键路径 |
| **Celery + Redis** | 跑通阶段引入独立队列与 broker 是净负担；用 asyncio + PG 状态表足够，但必须留 `TaskRunner` 接口 |
| **全双工实时语音** | 体验最好，但强依赖特定实时语音供应商，与 FR-A-01/FR-A-04「多供应商可切换」存在张力，且工程复杂度显著高于当前阶段所需 |
| **MinerU / 全量 OCR 链路** | 物料以技术文档为主，GPU 依赖与运维成本明显过度 |
| **Rerank 默认开启** | 提升精度但增加 200–500ms，出题延迟预算吃紧；改为保留接口，用 FR-A-13 评测数据决定 |
| **纯 `<audio>` 标签播放 TTS** | 无法可靠实现"随时中止播报"（FR-U-15）；必须用 Web Audio API + 播放队列管理器 |
| **把实时评分放进面试链路** | FR-U-19 明确要求不显示实时评分；且评分在链路内会放大延迟与不一致 |

## 7. 现在必须定死的事项（不可逆决策）

选型前提是"**先小规模跑通**、不做扩展性设计"与"**模型能力全部走云 API**"这两条，它们我认同——但以下 6 项**属于"现在多花 1 小时、将来省一周"的类别**，因为修改成本与已产生的数据量成正比，必须在编码前定死：

| # | 决策 | 为什么不可逆 | 建议 |
|---|---|---|---|
| 1 | **向量维度 = 1024** | 改 N 要改表结构 + 全量重嵌入 | 列类型写死 `vector(1024)`，chunk 表记录 `embedding_model_version`。**不可逆的是维度**；运行位置已定为云 API（§4.1），更换供应商只需重嵌入数据、不动表 |
| 2 | **版本字段进表结构** | 事后补字段 = 历史数据无法回算指标 | `llm_call_log` **每次调用记一条完整版本**（provider / model / prompt_version / rubric_version）；`reports` **按评分与复盘两次调用分别记录** `scorer_*` / `coach_*` 两组字段（两者模型与 prompt 可不同，见 §4.6 / §4.7），`rubric_version` 共用一份 |

| 5 | **`TaskRunner` 接口抽象** | 否则将来换队列要改遍所有业务代码 | 业务代码只调 `task_runner.submit(fn, ...)` |
| 6 | **`llm_call_log` 埋点** | 缺失的历史日志无法补算 6.1/6.2/6.3 | Phase 1 即建表并接入 Gateway |

## 8. 实施顺序与风险验证

### Phase 0 · 风险 spike（最优先，1–2 天）

**全项目最大的技术风险是语音延迟（1s / 1.5s）。** 但 2026-09-20 决策：**Phase 0 只求端到端流程打通，不以延迟数字为验收门禁**——延迟调优后置为独立阶段。

做一个最小闭环页面：

```
点击录音 → MediaRecorder 分片 → WS 推流 → 流式 ASR
→ 用户说完 → 触发 LLM → 首句切分 → 流式 TTS → 播放 → 可打断
```

**Phase 0 的验收口径（流程维度，不看延迟）**

| # | 验收项 |
|---|---|
| 1 | 录音能连续分片推流，并被流式 ASR 转写成文本 |
| 2 | 转写文本能触发 LLM 并拿到回复 |
| 3 | TTS 音频能分片推回前端并**顺序**播放 |
| 4 | 播放过程中能被新手录音打断，且**后端在跑的 LLM 流被真正取消**（不只是前端停播） |
| 5 | 无音频设备 / 播放失败时能降级为纯文字，**面试流程不中断** |

**拆两层测法，把变量解耦**（也让凭证需求更小）
1. **第一层**：只测 `ASR → TTS`，面试官发言用固定文本替代、不接 LLM → **只需语音凭证**，且语音延迟与 LLM 延迟可分开归因
2. **第二层**：接入真实 LLM，跑完整链路

**Phase 0 需要的凭证（外部依赖，需提前准备）**

| 能力 | 为什么需要 | 候选 |
|---|---|---|
| **ASR**（语音转文字） | 用户语音作答要转文字（FR-U-14） | 火山引擎（豆包语音）/ 腾讯云 / 阿里云 / 讯飞 |
| **TTS**（文字转语音） | 面试官发言要播报（FR-U-12） | 同上 |
| Embedding | Phase 2 才需要 | 任一输出 **1024 维**的服务 |
| LLM | 第二层测试才需要 | 任一 OpenAI Chat Completions 兼容或 Anthropic Messages 服务 |

> ⚠️ **两个容易踩的坑**
> 1. **ASR 与 TTS 是两个方向的能力，只准备一个不够。** 建议从**同一家**开通，减少鉴权、额度与控制台的集成面。
> 2. **必须开通「实时 / 流式」接口版本，不能选「基础」版本。** 基础接口是整句合成完才返回音频，用它就直接违背 §4.5 的流式设计——而事后改流式等于重写音频通道（见上文"形态不可后补"）。这一条在开通服务时就要选对。

> ⚠️ **一个不能后补的东西：流式链路「形态」**
>
> 延迟**指标**可以后置优化，但流式**形态**不行。
> - "录音分片推流 + 流式 ASR + 首句切分 + 流式 TTS + 播放队列 + 打断"是一整套前后端协议与状态机。若第一版做成"整段录音上传 → 整段文本合成 → 单文件播放"，后续改流式等于**重写音频通道**（协议、播放队列、打断信号、后端取消逻辑全换），不是参数调整。
> - 所以 Phase 0 建议**直接按流式形态搭骨架**，只是不把 1s / 1.5s 当门禁。**形态按要求实现，数字后置调优。**
> - 同理，**面试状态机与音频通道解耦**（§7 决策 4）必须在这一阶段就做对——它同样无法事后补救。

同时实测第二风险：**云 API 的 RPM / TPM 限制能否支撑出题并发**（§4.3 的并发度直接决定 NFR-01 能否达标）。

### 部署环境与资源约束

**目标服务器（阿里云 ECS，2026-09-21 确认）**

| 项 | 规格 |
|---|---|
| CPU | **2 vCPU** |
| 内存 | **2 GiB** |
| 系统盘 | 40 GiB |
| 峰值带宽 | 200 Mbps |
| 系统 | Ubuntu 24.04（华南1 · 深圳） |
| 公网 IP | 8.135.7.150 |

**结论：够用 —— 因为本架构是「薄编排 + 云能力」。** 服务端只做音频分片转发、编排调度、状态读写，**不做任何模型推理**。这些都是 I/O 密集型，2 vCPU 足够。

**这台机器的规格正是「全部模型能力走云 API」这条项目级约束的根因**（2026-09-21 决策）。四项能力本地化逐项不可行：

| 能力 | 本地化 | 原因 |
|---|---|---|
| ASR | ❌ | 中文可用模型（Paraformer 约 1 GB、Whisper 中量级更大）在 2 vCPU 上实时率不达标，且会吃满 CPU 拖垮编排服务；NFR-04 的准确率要求也达不到 |
| TTS | ❌ | 能达到"面试官"音质的方案（GPT-SoVITS / CosyVoice）需 1–4 GB 模型，CPU 生成 10 秒音频要数十秒；轻量方案（Piper）音质不匹配场景，首包 1s 更不可能 |
| Embedding | ❌ | `bge-m3` 约 2.3 GB，**2 GiB 内存装不下（会 OOM）** —— 这条把「Embedding 走云」从权衡项变成了硬约束 |
| LLM | ❌ | 7B 量化模型也要 4–5 GB |

> **「全云」的唯一例外：浏览器端的 VAD 与音频编码**
> `@ricky0123/vad-web`（Silero VAD，几 MB 的 ONNX）在**用户设备**上运行，不是服务端推理；`MediaRecorder` 的 Opus 编码同理。两者都在客户端，不占用服务器资源，也不违反"服务端不做模型推理"这条约束。**除此外没有任何本地模型推理。**

**内存曾经是瓶颈（不是 CPU）—— 把前端移出服务器后已不再贴线**

| 组件 | 内存预估 | 备注 |
|---|---|---|
| 系统 + Docker daemon | 300–500 MB | 改用 systemd 直跑可省约 150 MB |
| PostgreSQL 16 + pgvector | 250–400 MB | `shared_buffers` 需调低到 128 MB |
| FastAPI（uvicorn 单 worker，含静态文件托管） | 150–250 MB | |
| ~~Node 运行时（前端）~~ | **0 MB** | **前端不部署在服务器**（见上「必须做」第 3 条）；构建产物为静态文件，由 backend 托管 |
| 余量 | ≥ 700 MB | 音频分片、WS/SSE 连接、PDF 解析峰值 |
| **合计** | **0.7–1.2 GB** | 距 2 GiB 上限已有充裕空间 |

**因此必须做这 4 件事**

1. **加 2–4 GB swap**（40 GiB 盘足够）。2 GiB 跑多进程是贴线状态，swap 是防 OOM 的最后一道保险。
2. **不要在这台机器上跑构建**。`npm run build`、`pip install torch` 这类操作的内存峰值会直接 OOM。**构建在本地做，只把产物推上去。**
3. **前端不部署在这台服务器上**：React + Vite 构建出的是**纯静态产物**（`dist/`，即 index.html + assets/），由 backend（FastAPI）托管，从内存预算中直接省掉整个 Node 运行时。部署面因此简化为 `docker compose` 的 **postgres + backend 两个容器**。代价是放弃 SSR 能力——但本项目前端是登录后的工具型应用，**本就无 SSR / SEO 需求**，且所有数据都经 REST / SSE / WebSocket 从 FastAPI 取，音频处理全在浏览器端。
4. **PostgreSQL 严格限内存**：`shared_buffers=128MB`、`work_mem=4MB`、`max_connections=20`。

**带宽与磁盘都不是瓶颈**：音频是低带宽流（Opus 约 24 kbps），双向音频 + SSE 文本用不到 200 Mbps 的零头；40 GiB 盘按每场面试音频 2–4 MB 计，存量宽裕。

> ⚠️ **由"国内服务器"导出的一个重要约束：LLM 供应商必须选国内可直连的。**
> 深圳地域的 ECS 访问境外 API（OpenAI / Anthropic）通常不通或极不稳定，而 LLM 是 Phase 1 起就要用的核心依赖。因此：
> - LLM 优先选国内厂商（豆包 / 通义 / DeepSeek / Kimi / 智谱），它们多数提供 **OpenAI Chat Completions 兼容接口**，正好落在 §4.1 已支持的协议范围内，**协议选型不受影响**；
> - `AnthropicAdapter` 在本机环境下可能长期没有实际流量，但保留成本极低，且它是 FR-A-01「多供应商可切换」的组成部分，不必删；
> - **上机第一件事是实测目标 API 的连通性**，再定供应商——这比读文档可靠。
>

### 上线前置事项（静态托管相关）

前端改为「Vite 构建 + 后端托管」后，上线前必须处理以下 **5 件事**（v2.3 由 4 件增至 5 件）。前三件与前端部署形态直接相关，**第 2 件独立于部署形态，但最容易漏**。

> ★ **首版已定：纯内网自用，本组全部后置（v2.3，随待决策清单 N6 / I 组）**：以下 5 项**不阻塞开发与首版验收**，待确定要对外提供服务时**整批启动**。其中 **第 3 项（ICP 备案）是外部流程、有 2–3 周提前量**，**第 2 项（HTTPS）是语音功能的硬门槛**——两者属"现在要记住、到时不能忘"的事项。
>
> ⚠️ **唯一需要现在就记住的技术边界**：浏览器对麦克风的 secure context 豁免**只覆盖 `localhost` / `127.0.0.1`，不覆盖局域网 IP**（如 `192.168.x.x`）。所以"纯内网自用"的实际含义是：
> - **本机 `localhost` 访问 → 录音正常**，语音链路可完整开发与验收 ✅
> - **从另一台机器用内网 IP 访问 → `getUserMedia` 仍被拒**，语音功能不可用 ❌（需 Chrome 启动参数 `--unsafely-treat-insecure-origin-as-secure=http://<内网IP>:8000`，或自签证书）

**1. SPA fallback（必做）**

静态 SPA 的路由由 React Router 在浏览器端处理，服务端并不存在 `/interview` 这样的物理路径。不做回落的话，用户**刷新子路由会直接 404**。做法：在所有 API / WS 路由注册**之后**挂一个 catch-all，回落到 `index.html`。

```python
app.mount("/assets", StaticFiles(directory="static/assets"), name="assets")

# ⚠️ 必须放在最后：FastAPI 中注册顺序即匹配优先级
@app.get("/{full_path:path}")
async def spa_fallback(full_path: str):
    return FileResponse("static/index.html")
```

顺序写错会把 `/api/*` 一起吃掉——这是这类部署最常见的故障。

**2. HTTPS 与 `getUserMedia` 的 secure context 要求（最容易漏）**

浏览器规定 **`getUserMedia`（麦克风）只在 secure context 下可用**：

| 访问方式 | 麦克风 | 说明 |
|---|---|---|
| `http://localhost` | ✅ 可用 | 本地开发不受影响 —— **所以本地测不出这个问题** |
| `http://<公网IP>:非标准端口` | ❌ **被拒绝** | 语音作答链路整体失效（录音起不来） |
| `https://<域名>` | ✅ 可用 | 对外提供语音功能的唯一实际路径 |

**因此只要对外提供语音功能，就必须上 HTTPS** —— 这台服务器的公网 IP 无法签发受信任证书，实际做法是用域名 + 证书。**这才是上线的真正门槛，与前端部署形态无关。**

**3. ICP 备案（取决于是否用域名 + 80/443）**

- 跑通阶段：**公网 IP + 非标准端口自用 → 不需要备案**
- 对外提供服务：域名 + 80/443 → **需要 ICP 备案**

**4. WebSocket / SSE 的注意事项**

- 静态托管**不影响** WS 与 SSE —— 它们走 FastAPI 自己的路由，与静态文件互不干涉
- 前后端**同源部署**反而更简单：无跨域、无 Cookie SameSite 问题
- 若将来在 FastAPI 前加 Nginx 反代处理 TLS，**必须为 WS 路径透传 `Upgrade` / `Connection` 头**，否则 WebSocket 握手失败（音频流全断）。这是加反代时最常见的坑

**5. 管理端鉴权升级（v2.3 新增，随 N1 / A9）**

首版按 **A9** 用**管理员口令 + 可选 IP 白名单**保护管理端（用户端匿名）。**对外提供服务前必须升级为真实鉴权**（登录 + 会话/Token 管理），否则任何人都能修改模型供应商配置与密钥。

> **本组的登记位置**：这 5 项已同步登记进《待决策清单》的 **I 组 · 上线前置依赖**（I1–I5），便于对外时点到来时一次性勾清。
