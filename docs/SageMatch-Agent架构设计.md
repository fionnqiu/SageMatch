## 0. 一句话定位

EchoMind 是「路由驱动的多 Agent 客服运行时」；SageMatch 要的是「**状态驱动的多 Agent 面试训练运行时**」。

这个差别决定了哪些能直接搬、哪些必须改造。EchoMind 处理的是**无状态、单轮、可并行**的客服请求；SageMatch 面对的是**强状态、60 分钟连续、严格时序**的面试会话。所以：**编排思想沿用，状态管理必须重做**。

## 2. 五层架构总览

```
┌──────────────────────────────────────────────────────────────┐
│  ① 感知层 · 输入结构化                                        │
│     语音通道（VAD → 流式 ASR → 术语纠正）                      │
│     文本通道（岗位描述 → 三路融合维度识别 → 实体抽取）           │
└───────────────────────────┬──────────────────────────────────┘
                            │ 结构化表征（维度 / 实体 / 转写文本）
┌───────────────────────────▼──────────────────────────────────┐
│  ② 认知层（决策层）· 推理与决策                                │
│     Agent 角色契约 │ ReAct 双层循环 │ 结构化决策输出            │
│     确定性判定边界 │ 评分四步 + rubric 行为锚点                │
└───────────────────────────┬──────────────────────────────────┘
                            │ 行动意图（调工具 / 生成 / 打分）
┌───────────────────────────▼──────────────────────────────────┐
│  ③ 记忆层 · 跨轮状态与长期积累                                 │
│     工作记忆（最近 3–5 轮原文）│ 结构化面试纪要（JSONB）        │
│     能力画像（历次得分）      │ 全量原文（永不删除）           │
└───────────────────────────┬──────────────────────────────────┘
                            │ 读写（选择性注入 / 落库）
┌───────────────────────────▼──────────────────────────────────┐
│  ④ 行动层 · 与外部交互                                        │
│     工具层（9 + 1，白名单）│ 三路混合检索 + RRF               │
│     语音输出（首句切分 / TTS / 打断）│ 供应商 Gateway + 熔断降级 │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  ⑤ 协调 / 编排层 · 调度以上四层                                │
│     三类编排形态 │ 路由（分片/性能/降级）│ 并发限流 + TaskRunner │
│     健康度反馈路由 │ 评测与质量反馈闭环                        │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 层职责与归属

| 层 | 职责（一句话） | 归属模块 | 主要承载的 Agent | 关键需求 |
|---|---|---|---|---|
| **① 感知层** | 把非结构化输入变成结构化表征 | 语音通道、文本通道、三路融合维度识别 | `ProfileAnalystAgent` | FR-U-01、U-14、NFR-04 |
| **② 认知层** | 推理与决策：问什么、出什么题、给几分 | 角色契约、ReAct 循环、决策输出、评分流程 | `QuestionAuthor` / `QuestionCritic` / `Interviewer` / `Scorer` / `Coach` / `EvalJudge` | FR-U-03~06、U-10、U-20~U-23、6.1、6.2 |
| **③ 记忆层** | 跨轮状态与长期积累 | 工作记忆、结构化纪要、能力画像、全量原文 | —（被认知层读写） | FR-U-16、U-17、U-24 |
| **④ 行动层** | 与外部世界交互并对内落库 | 工具层、混合检索、语音输出、供应商 Gateway | —（被认知层调用） | FR-U-02、U-12~15、FR-A-01~04、NFR-10~12 |
| **⑤ 协调/编排层** | 决定谁在什么时候执行、并发多少 | 三类编排形态、路由、限流、反馈闭环 | —（调度认知层各 Agent） | FR-U-04、NFR-01、NFR-02 |

### 2.2 层间边界规则（硬约束）

没有边界规则的分层只是目录整理。以下 4 条必须靠目录结构 + lint 规则强制，否则分层会在两周内退化成"哪里方便写哪里"：

| # | 规则 | 为什么 |
|---|---|---|
| B1 | **认知层与感知层均不得直接调用任何供应商 SDK 或 HTTP**，只能经行动层的 Gateway | 这是 FR-A-01/04「切换供应商上层无感」唯一可靠的保障。**适用范围必须覆盖感知层**——`ProfileAnalystAgent` 的 LLM 调用与三路融合的 Embedding 路都在感知层，若不纳入约束，它们会成为绕过 Gateway 的第二个出口 |
| B2 | **认知层不得直接读写数据库**，一切持久化经行动层的工具 | 让记忆层的「全量存储 + 选择性注入」策略集中在一处，避免散落的读写破坏不变量 |
| B3 | **感知层不得依赖面试状态**，必须是无状态纯函数 | 保证语音/解析链路可独立测试；且这是 NFR-12「语音异常不中断面试」的结构性前提 |
| B4 | **编排层不写业务规则**，只做调度 | 业务规则混进调度器后，改一条规则要动并发逻辑，两者变更频率完全不同 |

### 2.3 角色判定标准（新增角色的准入条件）

多 Agent 系统的失败模式不是角色太少，而是**角色太多**。每新增一个角色都要付出 5 项成本（见文末），所以新增前必须过判据。

**判据（4 条全中才算 Agent）**

| # | 判据 | 说明 |
|---|---|---|
| **C1** | 有**决策空间** | 存在多个合理下一步，需依情况选择；流程固定的一律不算 |
| **C2** | 依赖**运行时外部信息** | 决策必须调用外部能力才能做出 |
| **C3** | **步数不确定** | 循环次数由情况决定，不由代码写死 |
| **C4** | 输出的是**决策**而非结果 | 能表达"我要做什么"，而不仅是"算出了什么" |

**按判据过筛现有 7 个角色**

| 角色 | C1 | C2 | C3 | C4 | 结论 |
|---|---|---|---|---|---|
| `ProfileAnalystAgent` 岗位分析师 | 弱（schema 约束） | ✗ | ✗ | ✗ | **LLM 模块** |
| `QuestionAuthorAgent` 出题官 | ✅ | ✅ 检索 | ✅ 重出 | ✅ | **自主 Agent** |
| `QuestionCriticAgent` 质检员 | ✅ | ✅ 判重/盲测 | ✅ 回边 | ✅ | **自主 Agent** |
| `InterviewerAgent` 面试官 | ✅ | ✅ 取原话 | ✅ | ✅ | **自主 Agent** |
| `ScorerAgent` 评分员 | ✗（固定三步） | 弱（取 rubric / 取原话） | ✗ | ✗ | **LLM 模块** |
| `CoachAgent` 复盘教练 | ✗（读冻结分数） | ✗ | ✗ | ✗ | **LLM 模块** |
| `EvalJudgeAgent` 质量审计员 | ✗ | ✗ | ✗ | ✗ | **LLM 模块** |

**结论：7 个角色中只有 3 个是真正的自主 Agent**（出题官、质检员、面试官，即走 ReAct 循环的那三个）；另外 4 个是 **LLM 驱动的确定性模块**（岗位分析师、评分员、复盘教练、质量审计员）——它们用 LLM，但没有自主决策空间，**不应按 Agent 的方式设计**（不需要循环、不需要工具协商、不需要状态）。

> 注意：评分与复盘之所以拆成两个模块（§4.6），是为了让"打分"与"写给用户看的文字"结构性隔离——**这不是在增加 Agent，只是把一次本来就独立的 LLM 调用换个归属**。

这个区分有实际意义：自称"多 Agent"不等于每个模块都要套 Agent 运行时。**把确定性模块包装成 Agent，只会白白引入循环开销与不确定性**——而 NFR-01（120s）与 NFR-02（1.5s）两个预算都很紧。

**明确不新增的角色**

| 候选角色 | 判据结果 | 正确归属 | 理由 |
|---|---|---|---|
| 切片员 Chunker | C1 ✗ C3 ✗ C4 ✗ | 行动层 Pipeline（解析 + 切分） | 切分粒度是**配置参数**，**本期不在管理端热改**（FR-A-05/06 后置到后端 config）；采用 Markdown 标题优先的递归切分，纯规则无分支 |
| 索引编排员 Indexer | C1 ✗ C2 ✗ C3 ✗ | 行动层 Pipeline + `TaskRunner` | embed + upsert 完全确定性。索引结构（HNSW 参数、分区策略）是**一次性工程决策**，不是运行时角色 |
| 检索员 Retriever | C1 部分 / C3 ✗ | 行动层工具 `hybrid_search` | 向量召回、BM25、RRF 融合都是确定性算法；唯一带 LLM 的「查询改写」是一次性 N=3，无循环 |

**为什么检索不该独立成 Agent（第一性原理）**

检索的目标函数由**消费者**定义：出题官检索是为了"出题有依据"，面试官检索是为了"验证用户回答里的某个说法"。如果把检索交给独立 Agent，它只能自己**猜**该检索什么——这就在「消费者意图 → 检索 Agent 的猜测」之间插进一次**不可逆的信息损失**。

所以本设计中 **query 构造权保留在消费方**（Agent 自己决定检索什么），`hybrid_search` 只是执行工具。这与边界规则 B2 同源：**能力下沉到行动层，决策留在认知层**。

EchoMind 同样如此：它有 4 个角色，但 RAG 不是其中之一——检索由 `MCPToolManager` + `KnowledgeBase` 承担（P4/P5），查询改写藏在 `search_with_rewrite` 工具内部。

**唯一会改变结论的情形：迭代式检索**

当检索从「一次性多路召回」变成「召回 → 评估够不够 → 不足则改写重试」的循环时，C1/C3 成立，这时才需要考虑检索角色。但即便如此，**优先做成 `hybrid_search` 内部的循环（工具内 ReAct），而不是新 Agent**——因为它只做一次"够不够"的判断，没有独立会话与状态。**只有当它需要独立的记忆与多轮交互时，才升级为 Agent。**

> 触发条件（到点再议，不在本期范围）：FR-A-13 评测显示「出题可用率 < 80% **且**归因于知识召回不足」。

**新增一个 Agent 的成本（5 项）**

| 成本 | 说明 |
|---|---|
| LLM 往返 | 直接吃 NFR-01 / NFR-02 的延迟预算 |
| Prompt 维护 | 版本号 + 回归评测 + 基线 |
| 权限边界 | 白名单需重新划分，且要防止越权 |
| 失败点 | 熔断 / 降级 / 重试路径都要设计 |
| **跨角色信息损失** | 每次传递都要把上下文压缩成输入契约，**有损且不可逆** —— 这是最容易被低估的一项 |

## 3. 感知层

**职责**：双通道输入 → 统一的结构化表征。这一层的输出是后续所有层的输入契约。

```
【语音通道】（面试作答）
麦克风 → 浏览器 VAD 判停（静音 600–800ms）
       → MediaRecorder 分片（timeslice=200ms）→ WebSocket
       → 流式 ASR（边推边出中间结果）
       → 术语纠正（知识库术语表 + 编辑距离/同音校正）
       → 低置信度片段标记
       ▼ 输出：转写文本 + 置信度标记

【文本通道】（岗位提交 / 管理员物料）
岗位描述（粘贴 / 上传）→ 解析
       ├─ 路1 LLM（权重 0.7）      抽取技能方向 / 知识领域 / 经验要求
       ├─ 路2 Embedding（权重 0.2） 与「标准维度库」做相似度 → 归一化维度命名
       └─ 路3 Pattern（权重 0.1）   抽取年限 / 学历 / 熟练度等级
       ▼ 加权融合 + 置信度阈值兜底
       ▼ 输出：结构化维度列表 + 实体 + source_scores
```

### 3.1 三路融合的移植（来自 EchoMind `IntentRecognizer`）

这是本项目最值得移植的单个模块。EchoMind 用它三路融合判定意图；SageMatch 用它做 **FR-U-01（岗位描述 → 考察维度）**：

| 路 | 权重 | 在 SageMatch 的职责 |
|---|---|---|
| LLM | 0.7 | 从岗位描述抽维度：技能方向 / 知识领域 / 经验要求 |
| Embedding | 0.2 | 与「标准维度库」做相似度匹配 → **归一化维度命名**（"熟悉分布式一致性协议" 与 "掌握共识算法" → 同一维度） |
| Pattern | 0.1 | 抽取硬性约束：年限、学历、熟练度等级（"精通" > "熟练" > "了解"） |

**输出不只是维度列表**，而是结构化结果 —— 直接对应 EchoMind 的 `IntentResult`：

```jsonc
{
  "dimensions": [
    { "name": "分布式一致性", "normalized_from": "熟悉分布式一致性协议",
      "type": "knowledge", "proficiency": "high", "confidence": 0.82,
      "source_scores": {"llm": 0.9, "embedding": 0.74, "pattern": 0.5} }
  ],
  "entities": {
    "skills": ["Go", "Kubernetes", "Raft"],
    "years": ["3-5 年"], "domain": ["云原生"], "degree": ["本科及以上"]
  }
}
```

**两个下游联动，价值很高**：

1. **置信度用于内部质量判定（v2.9 改写）**：原设计是「置信度驱动审核 UI」——那依赖 FR-U-02（用户确认/编辑维度），**该需求已随 PRD v1.7 删除**（维度识别结果自动生效，用户端无审核表单）。现在 `confidence` 与 `source_scores` 不再驱动用户界面，而是用于**两处内部用途**：① 维度列表在会话界面**只读告知**时可做视觉弱化标注（低置信维度显示得更淡，属展示而非交互）；② 更关键的是**供出题链路判断优先级**——低置信维度可在补生成阶段（§7.1 形态一的唯一回边）获得优先重试。**这两个字段因此仍有价值，只是消费方从"用户"变成了"系统自身"。**
2. **实体闭环进语音通道**：抽出的 `skills` 实体**动态注入 ASR 热词表 + 术语纠正词典**（即感知层内部的跨通道闭环）。这正是 NFR-04「专有技术名词识别错误不得影响追问判断」的实现方式，且随岗位自动变化。EchoMind 的 `entities` 喂给路由；SageMatch 的 `entities` 喂给语音识别。

### 3.2 边界说明

感知层**只做表征，不做判断**：它不决定"维度够不够"、不决定"该问什么"。这些属于认知层。这条边界让感知层保持无状态（规则 B3），从而可以被单测覆盖——输入一段岗位描述，断言输出维度列表。

## 4. 认知层（决策层）

**职责**：所有推理与决策。这一层是 Agent 本身。

> **归属说明**：§4.1 列出的 7 个角色中，**6 个归属认知层**；`ProfileAnalystAgent` 归属**感知层**（§2.1 与 §3.1 的三路融合），在 §4.1 一并列出只为保持角色清单完整。它虽是 LLM 驱动，但受边界规则 B1 约束（只能经行动层 Gateway 调用模型）。

### 4.1 Agent 角色清单

7 个角色，分**离线**与**在线**两组。刻意不设更多——PRD §7.2 明确要求不扩范围，**角色数量本身就是范围**。

按 §2.3 的判据（C1–C4）过滤，这 7 个里**只有 3 个是自主 Agent**（走 ReAct 循环，有决策空间与不定步数），另外 4 个是 **LLM 驱动的确定性模块**（单次结构化调用），不应按 Agent 方式设计：

| 分类 | 角色 | 是否走 ReAct |
|---|---|---|
| **自主 Agent（3）** | 出题官、质检员、面试官 | ✅ |
| **LLM 确定性模块（4）** | 岗位分析师、评分员、复盘教练、质量审计员 | ✗ |

**表 1 · 角色定位与边界**（「明确不做什么」比「做什么」更重要——多 Agent 系统最常见的失效不是职责不清，而是**职责重叠**）

| 角色 | 人类类比 | 职责（一句话） | **明确不做什么** |
|---|---|---|---|
| `ProfileAnalystAgent` 岗位分析师 | JD 拆解者 / 猎头顾问 | 把岗位描述拆成结构化考察维度 + 实体（技能词、年限、熟练度） | 不出题；不判断"维度够不够"；不接触面试 |
| `QuestionAuthorAgent` 出题官 | 命题老师 | 按**单个**维度检索知识并出题（题干/选项/答案/解析） | 不看其他维度的题；**看不到评分标准** |
| `QuestionCriticAgent` 质检员 | 审题组 / 教研质检 | 挑错：覆盖度达标吗、跨维度重复吗、干扰项有迷惑性但无歧义吗 | **不自己出题**（否则既是运动员又是裁判）；不做面试评判 |
| `InterviewerAgent` 面试官 | 真人面试官 | 多轮提问、基于历史回答追问、按覆盖度收尾 | **不打分、不透露评价**（FR-U-19）；不写解析 |
| `ScorerAgent` 评分员 | 面试评分委员 | 面试后：抽取证据 → 按 rubric 分维度打分 → 加权合成（**分数在此冻结**） | 不参与面试过程；**不写任何面向用户的文字**；不改写用户回答 |
| `CoachAgent` 复盘教练 | 复盘教练 / 培训师 | 基于**已冻结的分数与证据**生成失分点与可执行改进建议 | **不改写分数**；不重新判断证据；不产出题目或面试内容 |
| `EvalJudgeAgent` 质量审计员 | 教研抽检 / 第三方评估 | 管理端评测：出题质量四项指标、评分一致性 σ、排序稳定性 | 不产出面向用户的内容；结果只回流到**配置**，不回流入单次链路 |

**三条设置原则**：

1. **按「对抗关系」设角色，不按流程切分。** 出题官 ↔ 质检员是对手（一个生成、一个挑错）；面试官 ↔ 评分员是分离的（面试时不给分）；评分员 ↔ 复盘教练也是分离的（写评语的人天然有动机让分数好看，见 §4.6）。这样"挑错"才成为某个角色的**本职**，而不是大家都"顺便检查一下"——后者等于没人负责。EchoMind 的 `EscalationAgent`（专职交接而非继续回答）也是同一思路。
2. **权限用白名单硬隔离，不靠 prompt 约束。** 在 prompt 里写"请不要评分"是不可靠的，而工具列表里没有这个东西是可靠的。
3. **不是每个角色都需要 ReAct。** 只有「多步决策 + 需要外部信息」的才走循环（§2.3 判据）。

**表 2 · 运行时参数**

| 角色 | 时机 | 温度 | 走 ReAct | 行动层工具白名单 |
|---|---|---|---|---|
| `ProfileAnalystAgent` | 感知层产出后（**归属感知层**） | 0.1 | ✗ | — |
| `QuestionAuthorAgent` | 离线·**多实例并行** | 0.7 | ✅ 2 轮 | `hybrid_search`、`check_duplicate` |
| `QuestionCriticAgent` | 离线·汇聚 | 0.0 | ✅ 2 轮 | `check_coverage`、`check_duplicate`、`validate_question`、`blind_test_option` |
| `InterviewerAgent` | **在线·长会话** | 0.6 | ✅ 1–2 轮 | `get_turn_quote`（**<10ms 本地主键查询**，见 §6.1 在线约束） |
| `ScorerAgent` | 离线·面试后 | 0.0 | ✗ | `get_turn_quote`、`get_rubric` |
| `CoachAgent` | 离线·分数冻结后 | 0.3 | ✗ | 读冻结的分数与证据（无工具） |
| `EvalJudgeAgent` | 管理端（由编排层调度） | 0.0 | ✗ | `blind_test_option`、`rerun_scoring`、`check_coverage`、`check_duplicate`、`validate_question` |

> **本表是白名单的唯一权威源**（角色视角）。§6.1 的工具表（工具视角）必须与本表逐项一致；若出现分歧，以本表为准。
>
> **`ScorerAgent` 与 `CoachAgent` 的模型与 prompt 可分别选择**（§4.6）——评分用更强更稳的模型以保障 σ，复盘用更快更便宜的模型（它是最长输出）。因此 `reports` 表按两次调用**分别记录** `scorer_*` / `coach_*` 两组版本字段（见主选型文档 §4.7 与 §7 决策 2）。

**白名单的实质意义**：`InterviewerAgent` 绝不能持有 `blind_test_option`（评测工具，会泄漏答案与评分标准）；`QuestionAuthorAgent` 绝不能持有 `get_rubric`（出题时不该看到评分标准，否则会照着标准出题）。

EchoMind 的 `EscalationAgent`（不调 LLM，确定性产出）验证了同一条原则：**确定性节点不要用 LLM**。见 §4.3。

**对 EchoMind 的一处改进**：EchoMind 的 `_needs_escalation()` 用关键词扫文本判断是否升级，脆弱。SageMatch 的 Agent **输出结构化决策字段**而非自由文本：

```jsonc
// InterviewerAgent 输出契约
{
  "decision": "probe" | "advance" | "wrapup",
  "target_dimension": 3,
  "speech": "……",              // 文字形态，同步触发行动层的 TTS
  "citations": [8, 12]          // 引用的 turn_id，前端校验真实性
}
```

`decision` 让「动作」显式可记录、可评测，而不是靠事后猜文本意图。

### 4.2 ReAct 设计：两层循环 + 硬预算

这是对 EchoMind 模式**最重要的一处改造**。EchoMind 只有一层循环（`BaseAgent._call_llm` 的 `for _ in range(3)`），因为客服是单轮请求-响应。SageMatch 的面试是 60 分钟连续会话，因此需要两层：

```
┌─ 外层：会话循环（InterviewerAgent，30–60 分钟，无固定轮次上限）──────────┐
│                                                                        │
│   while not should_wrapup:                                             │
│     ┌─ 内层：ReAct 工具循环（单轮内，最多 2 次 LLM 调用）────────────┐  │
│     │  Thought  → 读结构化面试状态（已注入，见下）                   │  │
│     │  Action   → 需要精确引用时调 get_turn_quote(turn_id)          │  │
│     │  Observation → 工具结果（<10ms，行动层本地 PG 主键查询）        │  │
│     │  → 输出 {decision, speech, citations}                        │  │
│     └────────────────────────────────────────────────────────────┘  │
│     → 文字流式上屏 + 按句切分 → 行动层 TTS 流式播报                     │
│     → 用户作答 → 感知层转写 → 记忆层写入                               │
│     → 记忆层增量更新结构化纪要                                         │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

> ⚠️ **外层循环需要一个内部兜底**：FR-U-16 要求"不设固定轮次上限"，但 `while not should_wrapup` 若模型长时间不产出 `wrapup` 就会耗尽资源。因此编排层持有一个**内部安全阈值**（按轮次或时长），超阈值时强制进入收尾流程。该阈值**不对外暴露**，不构成对 FR-U-16 的限制。

**预算（在线面试单轮，约束 = NFR-02 的 1.5s）**

| 步骤 | 内容 | 预算 |
|---|---|---|
| 1 | 从记忆层组装上下文（结构化纪要 + 最近 3 轮原文） | 30 ms |
| 2 | LLM 调用：输出 `decision` + `speech`（流式） | 400–800 ms |
| 3 | 工具执行 `get_turn_quote`（行动层 PG 主键查询） | < 10 ms |
| 4 | LLM 调用：最终话术（仅在走了工具时发生） | 300–600 ms |
| 5 | 首句切分 + 流式 TTS 首包 | 300–600 ms |
| **常规轮次（1→2→5）** | | **0.7–1.4 s** ✅ |
| **引用轮次（1→2→3→4→5）** | | **1.0–2.0 s** ⚠️ |

> **引用轮次超标怎么办**（1.0–2.0s 已超出 NFR-02 的 1.5s，且主选型文档 §4.5 的过渡语预合成与 Filler **只覆盖"播报启动 ≤1s"，不覆盖这一情形**）。因此约定三级处理：
>
> 1. **优先零成本引用**——结构化纪要的 `answer_points[].quote` 已随上下文注入（§5.3），大多数引用直接用该原话片段即可，**不需要调工具**（即退化为常规轮次）；
> 2. 仅当需要**超出 `quote` 长度**的原文时才调 `get_turn_quote`，此时**复用过渡语 / Filler 掩盖**后端耗时，并把该轮标记为**延迟豁免轮次**；
> 3. **引用轮次占比纳入监控**（`llm_call_log` 统计），占比过高说明纪要中 `quote` 片段长度不足，应调长 `quote` 而非增加工具调用。

**因此定下两条硬性设计约束**：

**约束 A —— 高频只读状态从「工具调用」降级为「上下文注入」**
EchoMind 让 Agent 主动调 `search_knowledge_base` / `inspect_request_context` 去**取**状态。SageMatch 不能这样：把「已覆盖维度 / 已问问题 / 回答要点」每次都由模型决定去查，意味着每轮多一次往返。

正确做法：**记忆层的结构化纪要默认注入 prompt**，模型直接可答；工具只留给**低频的精确检索**（引用 20 分钟前的某句原话）。这让 70–80% 的轮次只需 1 次 LLM 调用。

> ★ **「下一题」也走同一条思路（v2.10 新增，H1）**：取题机制已定为**题集驱动**（§7.1 形态二）——**下一步该问哪道题，由编排层按覆盖进度直接算好、作为「当前待问题目」随上下文一并注入**，与 `covered_dimensions` / `asked_questions` 同批。
>
> **这不需要新增工具**：题面在出题时已落库（`questions` 表），属**零成本引用**；因此 **`InterviewerAgent` 的在线白名单仍然只有 #6 `get_turn_quote`（<10ms）**，§4.2 约束 B 的 <50ms 预算不变。若改成让面试官"走工具去取下一题"，就多一次 LLM 往返——**正是本条约束要避免的**。

**约束 B —— 在线 ReAct 循环内禁止任何网络调用或 LLM 调用**
EchoMind 的 ReAct 循环里可以调 LLM 做 rerank（`_rerank` 是一次 LLM 请求，几百 ms～秒级），客服场景没有硬延迟约束所以没问题。SageMatch 在线链路**不允许**——行动层工具执行预算硬性限制在 50 ms 内，只能是纯本地数据查询。重排、改写这类 LLM 工具**只允许出现在离线档**（见 §6.2）。

**预算（离线出题，约束 = NFR-01 的 120s）**

全链路（12 维度，**并发度 ≥ 8**，重出**限 1 次**）—— 与主选型文档 §4.3 **同源同表**，两处数字必须一致：

| 阶段 | 耗时 |
|---|---|
| 维度识别（感知层） | 10 s |
| 并行混合检索（行动层） | 1 s |
| 并行出题（12 维度 / 并发 ≥8 → 2 批） | 40 s |
| 去重 + 重复维度重出（约 20% 命中，并行） | 20 s |
| 质检（覆盖度 + 跨维度去重 + **抽样**盲测） | 20 s |
| 覆盖度补生成（仅缺失时触发，限 1 轮） | 0–15 s |
| 落库 + SSE 进度推送 | < 1 s |
| **合计** | **91 s（无补生成）/ ~106 s（含补生成）** ✅ 余 14–29 s |

> **120s 预算有多紧**：并发度掉到 6，出题从 2 批变 3 批（+20s），合计即 111s（含补生成约 126s，**已超标**）。所以 **并发度 ≥8 是设计要求（下限）**；若 Phase 0 实测上限 <8，须先做三件事之一——① 申请提高限流配额、② 降低单维度题量（2~4 题按 2 题出）、③ 把去重与质检进一步异步化——而不是直接放弃 NFR-01。上限由云 API 的 RPM/TPM 决定，**必须在 Phase 0 实测**。

### 4.3 确定性判定边界

把能用确定性算法解决的事交给算法，是这一层最容易被写坏的地方。SageMatch 明确划界：

| 判定 | 实现 | 是否用 LLM |
|---|---|---|
| 维度覆盖度 | 集合比对（`check_coverage`） | ✗ |
| 题干重复 | embedding cosine > 0.9（`check_duplicate`） | ✗ |
| 干扰项规则校验 | 选项长度方差 / 绝对化措辞 / 词面重叠 | ✗ |
| 题干自足性、解析与答案一致性 | `QuestionCriticAgent` 的 LLM 质检项（**不属 `validate_question`**，见 §6.1） | ✅（需语义理解） |
| 整体分合成 | 维度分 × 固定权重 | ✗ |
| 干扰项有效性 | 盲测（独立模型作答统计误选率） | ✅（必须是独立调用，见 §6.3） |
| 追问 / 出题 / 复盘文本 | 生成 | ✅ |

**「不用 LLM」不是省钱，是为了可复现。** 6.2 的评分一致性 σ ≤ 0.5 依赖「整体分 = 维度分加权」这一步完全无随机性。

### 4.4 评分流程：四步 + 行为锚点

σ ≤ 0.5 不能靠 `temperature=0` 达成 —— 即使温度为 0，跨供应商、批处理、浮点累加都会带来抖动。做法是把评分从"一次模型打分"改造成确定性流程，并**按角色切开**（§4.6）：

```
用户每轮回答
   ↓              ┌─────────── ScorerAgent（评分员，温度 0.0）───────────┐
[Step 1] 证据抽取（temperature=0，结构化输出）
   产出：优点 / 缺陷 / 支撑原话引用 —— 不含任何分数
   ↓
[Step 2] 维度打分（temperature=0，输入是 Step1 的结构化证据而非原始回答）
   rubric 含行为锚点：1-3 / 4-6 / 7-8 / 9-10 分别对应什么表现
   ↓
[Step 3] 加权合成（纯计算，零随机性，见 §4.3）
   ↓              └─────────────── 分数在此冻结 ────────────────┘
[Step 4] 生成复盘文本（温度 0.3，输入是已冻结的分数 + 证据，不重新判断）
                  └─────────── CoachAgent（复盘教练）───────────┘
```

**为什么要按角色切开**：Step 4 是唯一一次"要写给用户看"的调用。如果它与 Step 2 同处一个角色，模型可能为了让报告自洽而微调分数——即「叙事倒灌评分」。拆开后，`ScorerAgent` 的上下文里**根本不包含"要写给用户看的文字"这个目标**，隔离是结构性的而非靠 prompt 约定。

四个稳定性来源：证据先行（先看证据再看分，减少自由裁量）、行为锚点（把模糊的"好/差"变成可判定的行为描述）、权重固定 + 计算合成（随机性被压缩到维度分这一层）、版本锁定 + 缓存（`scoring_cache` 表以 `(answer_set_hash, dimension_id, provider_id, model, prompt_version, rubric_version)` 建唯一索引，同输入同版本直接命中）。

**分数冻结带来的一个额外好处**：复盘文案可以独立重生成（改写作风格不必重跑评分），因为它的输入是不可变的。这让文案迭代频率可以远高于评分标准迭代频率——两者解耦。

**按维度并行打分**：Step 2 按维度并行（每维度独立上下文）。这不只是提速——**每个维度独立调用能减少维度间上下文干扰，直接服务一致性要求**。

**评分粒度（口径定义）**：评分以「**每场面试 × 每个考察维度**」为最小单元——Step 2 的输入是该维度下所有轮次的回答证据；整体分由各维度分加权合成（Step 3，纯计算，**不单独缓存**）。因此 PRD §6.2 的"同一份回答"应理解为"同一场面试的回答集"。**v2.11 口径补充**：因 FR-U-20 已取消分项得分，**对外只呈现整体分**；「按维度并行 + 加权合成」仍为内部实现（用户端不展示任何分项）。PRD §6.2 注明：**一致性以维度分与整体分为测量对象，复盘文案不参与计算**（否则会把 `CoachAgent`（温度 0.3）的随机性误算进评分稳定性）。

### 4.5 可配置资产与版本化热加载

认知层的决策依据是三份可热更新的资产（对应 FR-A-06 的即时生效、FR-A-05 的参数可配）：

| 资产 | 目录 | 内容 | 消费方 |
|---|---|---|---|
| 评分标准 | `rubrics/*.md` | 维度定义 + 分数档**行为锚点** | `ScorerAgent`（评分） |
| Prompt 模板 | `prompts/*.md` | 各 Agent 的 prompt 主体 | 全部 Agent |
| 检索档位**默认值** | `retrieval_profiles.yaml` | §6.2 的档位参数**出厂默认值**（初始化时写入 `app_settings`，运行时的生效参数以库为准） | 行动层 |

**必须补上 EchoMind 缺的一环：版本号。** EchoMind 的 `learn()` 更新模板后只是 `self._cache.clear()` —— 没有版本概念。SageMatch 不能这样：**评分可复现的前提是能锁定"这份评分是哪版 rubric 算出来的"**。

做法：每次热加载对文件内容取哈希作为版本号，写进 `prompt_version` / `rubric_version`，随埋点落库（记忆层）。否则一旦出现评分不一致，无法分辨是**模型换了**还是**标准改了**。

### 4.6 评委的角色拆分（已采用方案 C）

**状态：已定稿**（2026-09-20 确认拆分）—— 本节保留当时的对比过程作为决策记录

**背景**：评分原本由单个 `ReviewAgent` 承担 §4.4 的四步——证据抽取 → 维度打分 → 加权合成 → 复盘文本。其中评分要确定性（保护 6.2 的 σ ≤ 0.5），复盘文本要可读性（温度 0.3）。两种目标的张力集中在同一个角色里。

**三个候选方案**

| 方案 | 做法 | LLM 调用次数 | 评分纯度 | 权限隔离 |
|---|---|---|---|---|
| **A** 不拆 + 复盘合并进打分调用 | 打分那一次调用直接吐出报告文字 | **最少**（省 1 次） | ✗ 最差 | ✗ |
| **B** 不拆 + 复盘独立调用（当前设计） | 同一角色内两步，靠 prompt 约定"不重新判断" | 中 | ⚠️ 中（**软约束**） | ✗ |
| **C** 拆成 `ScorerAgent` + `CoachAgent` | 评分三步归前者，复盘文本归后者 | 与 B **相同** | ✅ 物理隔离 | ✅ **硬约束** |

**关键事实（推翻了"拆分更贵"的直觉）**：**方案 B 与 C 的 LLM 调用次数完全相同**——因为复盘文本本来就必须是独立的一次调用。所以拆分**不增加任何延迟或调用成本**，只是把这次调用换个归属。

**拆分的优势**

| # | 优势 | 说明 |
|---|---|---|
| 1 | **抗"叙事倒灌评分"** | 拆开后评分方的上下文里根本没有"要写给用户看的文字"这个目标，分数生成与叙事生成从**结构上**隔离。这是对 σ ≤ 0.5 这个硬指标最直接的保障 |
| 2 | **权限可硬隔离** | `ScorerAgent` 无任何面向用户的输出通道；`CoachAgent` 不可写分数。消除了原先 `ReviewAgent` 持有的"复合权限" |
| 3 | **缓存与幂等边界干净** | 分数一经算出即**冻结不可变**，复盘文本可独立重生成。不拆则改文案要连带重跑评分，或依赖"只跑 Step 4"这种隐式契约 |
| 4 | **评测归因更准** | FR-A-14 测 σ 时可只对 `ScorerAgent` 做 N 次重跑，测量对象单一。耦合状态下 σ 异常无法区分是"评分逻辑不稳"还是"文案生成干扰了打分" |
| 5 | **模型可分别选** | 评分用更强/更稳的模型，复盘用更快更便宜的模型（复盘是最长输出）——**可能反而省钱** |
| 6 | **不增加"自主 Agent"数量** | 两者都不满足 §2.3 的 C1–C4，同属「LLM 确定性模块」。拆分**不违反**"不要随便加角色"的原则，角色从 3 自主 + 3 模块变为 3 自主 + 4 模块 |

**拆分的代价**

| # | 代价 | 说明 |
|---|---|---|
| 1 | Prompt 维护量 +1 | 两条 prompt 各自的版本号与回归用例。但两者变更频率不同，独立演进其实更清晰 |
| 2 | 上下文重复加载 | `CoachAgent` 需重新加载 Step 1 的证据与原话，多一份 token 开销（可由 PG 读取，无需重算） |
| 3 | 新增一个数据契约 | 分数 + 证据的结构需冻结为 `CoachAgent` 的输入。**但该结构已存在**（`reports` 表的维度得分 JSONB），无需新设计 |
| 4 | 编排节点 +1 | 复盘链路是纯线性（评分 → 冻结 → 生成报告），无分支，编排开销很低 |

**决定：采用方案 C（拆分）→ `ScorerAgent` + `CoachAgent`**

用方案 B 是在**用一个硬验收指标（σ ≤ 0.5）去换一点实现简洁**：B 的保护只是一句 prompt 约定（软约束），C 是结构性隔离（硬约束）。而对一个首版必须达标的指标，用软约束不划算。同时方案 A 被排除——它唯一的价值是省 1 次调用，代价是把"叙事倒灌评分"的风险推到最大。

**落地要点**（已同步到 §2.1 / §4.1 / §4.4 / §6.1 / §8）

| 项 | `ScorerAgent` 评分员 | `CoachAgent` 复盘教练 |
|---|---|---|
| 负责步骤 | Step 1–3（证据 → 打分 → 加权合成） | Step 4（复盘文本） |
| 温度 | 0.0 | 0.3 |
| 工具白名单 | `get_turn_quote`、`get_rubric` | 无（读已冻结的分数 + 证据） |
| 硬边界 | **无任何面向用户的输出通道** | **不可写分数**、不重新判断证据 |
| 模型选择 | 可用更强/更稳的模型 | 可用更快更便宜的模型（最长输出） |

- **分数一经合成即冻结（不可变）**，复盘文案可独立重生成 → 文案迭代频率可远高于评分标准迭代频率
- **FR-A-14 测 σ 时只对 `ScorerAgent` 做 N 次重跑**，测量对象单一，σ 异常可直接归因

> 若将来回退到不拆分，必须把触发条件写进验收：FR-A-14 实测 σ > 0.5，或复盘报告出现"分数与证据不匹配"的痕迹时立即执行拆分。

## 5. 记忆层

**职责**：跨轮状态与长期积累。EchoMind 的三层记忆（P6）分层思想完全适用，但**中间层的实现必须换掉**。

| EchoMind | SageMatch | 为什么必须改 |
|---|---|---|
| 工作记忆：Redis 最近 20 条 | **最近 3–5 轮原文**（从 PG 读，Redis 可选缓存） | 一致；但 Redis 非必需，**跑通阶段可省** |
| 情景记忆：ChromaDB **语义检索**压缩摘要 | **结构化面试纪要（JSONB，按 `turn_id` 索引）** | ⚠️ 语义检索是**概率性召回**，而 6.3 要求历史引用准确率 **≥95%**。要精确引用「第 4 轮」，不能用相似度检索 |
| 用户画像：长期偏好 | **能力画像**：历次各维度得分、薄弱项、变化记录 | 一致。**★ v2.9：本项已降为记忆层内部机制——PRD v1.7 删除了 FR-U-25「成长趋势视图」，用户端不暴露画像页面；画像现仅供 `CoachAgent` 生成复盘时引用历史场次做文字对照**（技术文档 §4.7 的 `growth_profiles` 表） |
| 压缩：≥15 条时**压缩并丢弃**旧消息 | **每轮结束增量更新纪要；原文全量持久化，永不删除** | ⚠️ 见 §5.1 |

### 5.1 最关键的一条差异：不丢原文

EchoMind 的 `_compress()` 会把旧消息从 Redis 删除，只留摘要 + 最近 5 条。理由充分——客服的历史细节不必要。

**SageMatch 绝对不能这样**，因为：
- FR-U-24 要求「查看完整历史与**对话回放**（含文字与语音作答内容）」
- FR-U-21 要求复盘指出「**第 4 轮**追问的回答过于笼统」——精确定位到轮次
- FR-U-17 要求面试官能准确引用 **20 分钟以上**的回答

所以采用 **「全量存储 + 选择性注入」**：

```
存储层：interview_turns 表保留每一轮原文（文字 / 语音路径 / 转写 / 作答方式），永不删除
             ↑
注入层：送往认知层的上下文 =
          系统提示（角色 + 考察维度；评分不在此处）
        + 结构化面试纪要（全量事实，JSONB）
        + 最近 3–5 轮原文
        + 当前主题
             ↑
按需层：需要引用任意历史轮 → 行动层 get_turn_quote(turn_id) 精确取原文（<10ms）
```

EchoMind 的压缩是「防止 context 爆炸」的手段；SageMatch 用「结构化纪要压缩**事实层** + 按需取原文」达到同样目的，**同时不损失可引用性**。

### 5.2 增量更新 vs 批量压缩

EchoMind 在达到阈值时**批量**压缩（`COMPRESS_AT = 15`）。SageMatch 必须**每轮结束即增量更新**纪要——否则在两次压缩之间的窗口里，认知层看不到最近的事实条目，正是「忘记前文」的成因。

用低成本模型做纪要增量更新（每轮一次轻量调用）。它不在用户等待的关键路径上（可与用户说话并行），开销可接受。

### 5.3 结构化面试纪要字段

```jsonc
{
  "covered_dimensions": [
    { "dimension_id": 3, "status": "covered", "depth": "shallow" }
  ],
  "asked_questions": [
    { "turn_id": 7, "dimension_id": 3, "question": "…", "intent": "验证并发模型理解" }
  ],
  "answer_points": [
    { "turn_id": 8, "quote": "我用了 channel 做同步…",
      "assessment": "缺少背压处理", "answer_mode": "voice" }
  ],
  "pending_probes": ["背压处理", "channel 缓冲区设计"]
}
```

`answer_points[].quote` 与 `turn_id` 是**引用溯源的基础**：认知层要求面试官追问时以 `[[turn:8]]` 形式标注来源，前端校验该 turn 是否真实存在（**防幻觉引用**），并记录校验失败率——这就把 6.3 的「历史引用准确率」变成了可自动计算的指标，而非靠人工抽查。

### 5.4 记忆层的其他内容

| 内容 | 用途 |
|---|---|
| 题目集 / 已生成题干池 | 出题时的**避让池**（FR-U-05 的生成时去重）；也是 6.1 四项指标的原始数据 |
| 岗位与维度 | 面试与出题的共同依据 |
| `llm_call_log` | 所有 LLM 调用埋点 —— 6.1 / 6.2 / 6.3 指标计算的唯一数据源 |
| `agent_traces` | Agent 决策与工具调用留痕 —— 多 Agent 链路的可解释性 |
| `eval_runs` + 基线 | 评测历史与回归对比（FR-A-15） |
| `provider_health` | 供应商健康度（供编排层路由） |
| `audit_logs` | 管理端变更留痕（NFR-08） |

> `llm_call_log` 是隐形的关键表：所有验收指标都要靠它算。**必须在 Phase 1 就建好**，等到做评测模块时才想起埋点，历史数据已缺失、无法回算。

## 6. 行动层

**职责**：与外部世界交互，并对内落库。认知层提出的意图在这里被执行。

### 6.1 工具层 + 白名单

沿用 EchoMind 的 `AgentToolSpec`（P4）。**9 个工具 + 1 个改为上下文注入的伪工具**（「可调用方」一列与 §4.1 表 2 逐项一致，**表 2 为权威源**）：

| # | 工具 | 档位 | 可调用方 | 实现 | 预算 |
|---|---|---|---|---|---|
| 1 | `hybrid_search` | 离线 | Author | 见 §6.2 | 秒级 |
| 2 | `check_coverage` | 离线 | Critic, Judge | PG 集合比对（**确定性，非 LLM**） | <20 ms |
| 3 | `check_duplicate` | 离线 | Author, Critic, Judge | 题干 embedding cosine > 0.9 | <300 ms |
| 4 | `validate_question` | 离线 | Critic, Judge | **纯计算规则**：选项长度方差 / 绝对化措辞 / 选项词面重叠 / 答案唯一性（选项文案互不重复） | <50 ms |
| 5 | `blind_test_option` | 离线 | Critic（抽样）、Judge（全量） | 独立 LLM 盲测 | 秒级 |
| 6 | `get_turn_quote` | 在线 | Interviewer、Scorer | PG 按 `turn_id` 主键查询 | **<10 ms** |
| 7 | `get_rubric` | 离线 | Scorer | 取当前 rubric 版本（含行为锚点） | <10 ms |
| 8 | `rerun_scoring` | 离线 | Judge | 同回答重复评分 N 次 | 秒级 |
| 9 | `list_glossary_terms` | 在线 | **行动层 · 语音输出链路**（非认知层角色） | 维度技术名词 → ASR 热词 | <10 ms |
| — | ~~`get_interview_state`~~ | — | ~~Interviewer~~ | **不作为工具，改为上下文注入**（§4.2 约束 A） | — |

**在线工具集的硬约束（对应 §4.2 约束 B）**：`InterviewerAgent` 的在线白名单**只有 #6 `get_turn_quote`（<10ms）**，满足 <50ms 预算。

- `check_coverage` **不进在线白名单** —— 维度覆盖进度（`covered_dimensions`）已随结构化纪要注入上下文（§4.2 约束 A），面试官走工具去"查"只会多一次 LLM 往返，而结果与注入的内容相同。
- `hybrid_search`（≥300ms）**不进在线白名单** —— 理由见 §6.2 的档位说明；面试所需知识在面试前一次性预取（主选型文档 §4.2）。

**`validate_question` 为什么独立成一个工具**：它是 §4.3「确定性判定边界」里"干扰项规则校验"的落地载体。抽成独立工具而不是写在 Critic 的 prompt 里，是因为：
- 规则判定必须**可复现**（与评分同理），prompt 里的规则执行不稳定；
- 它是**纯计算**（<50ms），放进 ReAct 循环不占延迟预算；
- 出题链路（Critic 全量）与管理端评测（Judge）**共用同一套规则**，否则"业务链路合格"与"评测指标合格"会出现口径不一致。

> **边界（重要）**：`validate_question` 只做**可计算**的判定。原先一并列入的"题干自足性""解析与答案一致性"需要语义理解，**不属这个工具**——它们由 `QuestionCriticAgent` 的 LLM 质检项承担（管理端评测则由 Judge 复用同一条 Critic 链路）。把 LLM 判断混进"确定性规则"会让口径失控：规则项必须可复现，语义项必须可迭代，两者的回归测试方式完全不同。

**不属于工具的两项能力（避免遗漏）**

| 能力 | 归属 | 为什么不列为工具 |
|---|---|---|
| 标准维度库的相似度匹配（§3.1 三路融合的 Embedding 路） | 感知层内部模块 | 感知层不是 Agent（§2.3），不参与工具分发；它是维度识别的内部一步 |
| 结构化纪要的读取与组装（§4.2 约束 A） | 编排层组装 + 记忆层读取 | 高频只读状态走**上下文注入**，走工具反而多一次 LLM 往返 |

沿用 EchoMind 的三件套：**JSON Schema 参数校验**（required / type / additionalProperties）、**TTL 缓存**、**三态熔断 + fallback**。这三者直接服务 NFR-10（不静默失败）与 NFR-11（重试不产生重复内容——重试用幂等键 + 结果缓存）。

### 6.2 混合检索：三路召回 + RRF 融合

EchoMind 的检索优化链路（P5）只有**向量**一路召回（ChromaDB 内置 MiniLM），靠**查询改写**扩成多路。SageMatch 需要**真混合**，因为技术文档里专有名词（"Raft 选举超时" vs "Paxos 选举超时"）纯向量会漂移。两者结合成三路：

```
query
├─ 路1  向量召回（原 query）              pgvector HNSW, cosine, top-15
├─ 路2  关键词召回（原 query）            tsvector BM25 + pg_trgm, top-15
└─ 路3  改写子查询召回（N=3 个角度，向量） pgvector, top-10 each  ← 来自 EchoMind P5
          ↓  三路 asyncio.gather 并行
   RRF 融合（Reciprocal Rank Fusion, k=60）+ 内容哈希去重    ← EchoMind 的 md5 去重
          ↓
   Rerank（接口保留，默认关闭）                              ← EchoMind 的 LLM 重排
          ↓
   top-8 送认知层
```

**检索档位化 `retrieval_profile`（关键决策）**：参数按档位分离。**本期实际只启用 `offline` 一档**。**v2.12**：RAG 数值参数不在管理端热改（FR-A-05/07 后置/收窄）。

| 档位 | 起用路 | 改写 | 重排 | 延迟目标 | 用于 |
|---|---|---|---|---|---|
| `offline` | 路1 + 路2 + 路3 | ✅ LLM 改写 N=3 | 可开 | 秒级可接受 | 出题、召回测试、管理端评测、**面试前置准备** |
| `online` | 路1 + 路2 | ✗ | ✗ | ~300 ms | **本期无启用场景（预留）** |

> **为什么 `online` 档本期不用**：原设计设想它服务"面试中追问前的知识补检索"，但这与两件事冲突——
> ① §4.2 约束 B 规定在线 ReAct 工具预算 <50ms，而 `online` 档是 ~300ms，**直接超标**；
> ② 更根本的是，**面试官的职责是追问用户的回答，不是输出领域知识**。它判断"要不要深挖某一点"的依据是用户回答里的含糊处（来自记忆层），不是知识库。若让它查知识库来评判答案对错，实际上是在面试中做隐含评分，违反 FR-U-19 的立意。
>
> 因此面试所需的知识改为**面试开始前一次性预取**（`offline` 档，按维度检索）并缓存进面试记录，面试中只读缓存。`online` 档作为参数化机制的一部分保留，待真有低延迟检索场景时再启用。

档位选择由编排层依据链路类型决定；**档位的生效参数以 `app_settings` 表为唯一权威源**（`retrieval_profiles.yaml` 仅作出厂默认值预设，初始化时写入库，运行时不读文件——见主选型文档 §4.2）；档位定义本身属认知层资产（§4.5）。管理端 FR-A-12 的召回测试可切换档位对比，**直接支撑 FR-A-07 的「可对比」**；返回结果需标注每段内容来自哪一路，否则无法解释调参效果。

**查询改写用于维度识别（延伸用法）**：EchoMind 的 `rewrite_query` 把「退款流程」扩成三个角度。SageMatch 可同法把**考察维度**扩成检索式：维度「熟悉分布式一致性协议」→ `["Raft 选举机制", "Paxos 与 Raft 区别", "分布式共识的容错边界"]`。这让出题时的知识召回同时在三个语义角度展开。

### 6.3 盲测的档位分离

干扰项有效性（6.1 的 20%–50%）靠盲测实现：只给题干 + 选项、不给知识内容，让**独立**模型作答并统计误选率。一次盲测 = 一次 LLM 调用，36 道题全测 = 36 次调用 ≈ 25s（并发 8）。

因此按链路分档：

| 链路 | 质检强度 | 原因 |
|---|---|---|
| **业务出题链路** | 规则校验全量 + 盲测**每维度抽 1 题** | 受 NFR-01 的 120s 硬约束 |
| **管理端评测（FR-A-13）** | 盲测**全量** | 无延迟约束，要的是准确指标 |

### 6.4 语音输出

```
认知层产出 speech（文字，流式）
  ├─ 文字同步上屏（FR-U-12 的文字形态）
  └─ 按句边界切分（。！？\n，或首句最小字数 12 字）
       └─ 逐句流式 TTS → 音频分片经 WS 推送
            └─ 前端 AudioQueue 顺序播放，可随时 interrupt
```

**打断的关键实现**（FR-U-15）：前端 `AudioQueue.stop()` 清空播放队列只是第一步 —— **必须同时把 `interrupt` 信号回传，取消正在跑的 LLM 流**（`asyncio.CancelledError`），否则后端会继续生成并推送音频，既浪费 token 又造成"打断了还在说"的错乱。

**降级**（NFR-12）：`AudioOutputManager` 监听 `AudioContext.state`、播放失败、无音频设备等信号，触发降级为纯文字。**硬性前提：面试状态机必须与音频通道完全解耦**——音频只是渲染层的一种输出通道，任何音频异常都不允许影响面试流程推进（即边界规则 B3）。这条如果做错，后面几乎无法补救。

### 6.5 供应商 Gateway

> **前置约束（项目级）**：**全部模型能力走云 API**（LLM / Embedding / ASR / TTS 四项均不自建），且候选**限定为国内可直连的服务**——目标服务器在深圳，境外 API 通常不可达。此约束来自服务器规格（2 vCPU / 2 GiB，`bge-m3` 约 2.3 GB 装不下内存等），完整论证见主选型文档 §8。**因此行动层没有任何本地推理。**

四类能力各自的适配器与协议翻译：

| 适配器 | 目标端点 | 必须处理的真实差异 |
|---|---|---|
| `OpenAIChatAdapter` | `/v1/chat/completions` | 基准，无额外翻译。同时覆盖所有宣称 OpenAI 兼容的第三方服务（**国内厂商多数走这条**） |
| `AnthropicAdapter` | `/v1/messages` | system 是独立字段非 message；tool schema 字段名不同；`tool_result` 必须回传为 user role 的 content block；`max_tokens` 必填；流式事件体系不同 |
| `EmbeddingAdapter` | 各家的 embeddings 端点 | **必须输出 1024 维**（维度已锁定）；批量接口的批大小与限流差异 |
| `ASRAdapter` / `TTSAdapter` | 各家国内云服务 | 流式接口形态、热词表注入方式、首包延迟差异 |

**本期不支持 OpenAI Responses 协议**：与 Chat Completions 结构不通用（`input`/`output` item、`instructions` 独立字段、`previous_response_id` 会话串联），而其覆盖的供应商范围已被 Chat Completions 完全包含。结构化输出策略：**tool calling 强制 schema 优先 → JSON mode + Pydantic 兜底 → 校验失败回灌修复（最多 2 次）**。

**能力协商**：每个供应商在配置中声明能力矩阵（流式 / tool / 结构化输出 / 多模态），Gateway 路由前检查，不支持则降级到备选策略而非直接报错（NFR-10）。

**Embedding 的特殊性**：更换 embedding 模型意味着**向量空间不兼容，必须全量重嵌入**——所以它**不参与"随手切换"**，但**不等于"不能换"**：因向量维度已锁定 `vector(1024)`，换供应商只需重跑物料入库，**不动表结构**（见主选型文档 §4.1 的"维度不可逆 / 运行位置可切换"两轴）。因此 embedding provider 独立于 LLM provider 配置；向量列维度写死在表结构；每条 chunk 记录 `embedding_model_version` 作为迁移依据。

## 7. 协调 / 编排层

**职责**：决定谁在什么时候执行、并发多少、失败了怎么办。这一层**不写业务规则**（边界规则 B4）。

### 7.1 三类编排形态

EchoMind 只有一种形态：`请求 → 路由 → 1 或 N 个 Agent → ResponseComposer 合并`。SageMatch 需要**三种**，因为有三个目的不同的链路。

**形态一 · 扇出–汇聚（出题）**

```
识别出的维度列表 [D1..DN]（来自感知层，**自动生效，无用户确认**）
   │
   ├─ 按维度分片（天然路由，不需要分类器）
   ▼
QuestionAuthorAgent × N         ← asyncio.gather + Semaphore 限流
   │  (每实例：hybrid_search → 出题 → check_duplicate → 必要时重出)
   ▼
QuestionCriticAgent（汇聚）
   │  ① 覆盖度集合比对  ② 跨维度题干去重
   │  ③ 干扰项规则校验  ④ 抽样盲测（每维度抽 1 题）
   ▼
缺失维度？──是──► 回补一次（唯一回边）
   │否
   ▼
题目集落库（记忆层）+ SSE 进度
```

> **本条链路的位置（v2.7 明确，v2.8 补用途唯一性，v2.9 精确化）**：形态一的产出是**题目集**，**只服务于两个目的**——① **面试提问的依据**（维度 → 具体问题的映射）；② **管理端出题质量评测（FR-A-13）的验证对象**（6.1 四项指标的计算基础）。
>
> ★ **用途唯一性（v2.9 更新）**：**出题能力的唯一消费方是「模拟面试」与「管理端评测」。** 题目集**不面向用户作答**——不做答题界面、不做判分、不做错题组织。经 PRD v1.7 的第二次收缩，**连"查看视图"这条出口也已取消**（原 v2.8 所述的"题目集页仅查看"已随该页面删除）：题目在用户端**只随面试官的提问节奏逐题以卡片形式浮现**（PRD FR-U-11，形态二/面试界面内）。**因此用户侧唯一出口是面试，管理端评测是旁路出口。**
>
> **它不是面向用户的交付终点**：PRD v1.5 已删除答题板块（原 FR-U-10 ~ U-13），PRD v1.7 又删除了题目集页面与维度确认环节——**用户从提交岗位到题目就绪全程无需任何操作**，就绪后直接发起模拟面试。因此形态一**不含**作答、判定与作答记录，**也不含任何面向用户的题目列表呈现**。但这**不改变形态一本身的设计**：扇出–汇聚、唯一回边、四步汇聚质检全部保留。
>
> ⚠️ **形态一不可随用户端页面一并删除**。它在架构上承担两件不可替代的事：① 让 §4.1 的 3 个自主 Agent 中的 2 个（出题官 + 质检员）有存在的理由；② 为 §7.5 的评测闭环提供**业务链路参照**——若连出题一起删，FR-A-13 就只能在两套出题实现之间自证（§7.5 明确禁止），评测意义被架空。**可以删的是"作答交互"与"查看页面"，不是"出题能力"。** 经过两轮收缩，形态一已完全变成**"看不见但必须在"的支撑层**。

**与 EchoMind 的关键差异**：EchoMind 的路由需要 `_domain_scores()` 打分器去**猜**该派给谁；SageMatch 的维度列表已是结构化数据，**分片是确定的，不需要打分器**。这是「状态驱动」对「分类驱动」的替代——有结构化状态时不要引入分类器。

**形态二 · 长会话 + 内层 ReAct（面试）**

不进并行分支，直接进 `InterviewerAgent` 的会话循环（§4.2）。

> ★ **取题策略：题集驱动 + 题内自由追问（v2.10 新增，H1）**
>
> PRD FR-U-11 要求"面试官问到某题时该题以卡片浮现"，而面试官是**自主 Agent**（走 ReAct、会依用户回答动态追问）——因此"**面试官问什么**"与"**题目集里有什么**"必须显式对齐。**本期口径**：
>
> | 维度 | 口径 |
> |---|---|
> | **取题主线** | **题集驱动** —— 面试官从题目集**按顺序取题**，保证**每道被问到的题都有卡片可渲染**，且与 **FR-U-04 的覆盖率 ≥90% 天然自洽** |
> | **题内追问** | **不受限** —— 在**同一道题内**，面试官可依用户回答**自由多轮追问**（FR-U-10 的能力完全保留） |
> | **取下一题的实现** | 由**编排层按覆盖进度算好并注入上下文**（§4.2 约束 A），**不是工具调用** —— 不增在线 LLM 往返、不破坏 <50ms 预算、**在线白名单不变** |
> | **自主体在哪** | 体现在**题内怎么追问、追问几轮、何时标记该题已覆盖**；**不体现在"问哪道题"** |
>
> **为何不做"面试官驱动"**（面试官自由决定问什么，问到的题才去题目集取卡片）：它更"自然"，但会**问到题目集里没有的题**（此时无卡片可展示，需额外定义降级行为），且会让 **FR-U-04 的覆盖率失去约束力**。两个代价都高于收益。

**形态三 · 按维度并行打分（复盘）**

`ScorerAgent` 的 Step 2 按维度并行（§4.4）。这不只是提速：每个维度独立上下文能减少维度间干扰，直接服务 6.2 的一致性要求。此后 `CoachAgent` 串行读取冻结结果生成报告（纯线性，无分支）。

### 7.2 路由

| 路由类型 | 信号 | 说明 |
|---|---|---|
| **分片路由** | 维度列表 | 确定性，出题链路的默认路由 |
| **性能路由** | Agent 成功率 / 延迟 / 惩罚项 | 同类多实例时选 `routing_score()` 最高者（EchoMind P2） |
| **降级路由** | 失败 / 熔断状态 | 专属 Agent 不可用时退到通用能力；不得静默失败（NFR-10） |
| **供应商路由** | 健康度（§7.4） | 同一能力的多个供应商之间选择 |

**Agent 池设计**：`Dict[AgentType, List[BaseAgent]]` —— 用 list 不是因为现在有多个实例，而是为同角色多实例、同类型不同模型配置、在线表现差异化路由留出结构空间（沿用 EchoMind 的做法）。

### 7.3 并发限流、任务执行与进度

- **并发限流**：出题链路的 `asyncio.Semaphore` 上限由云 API 的 RPM/TPM 决定（§4.2 的 120s 预算直接依赖并发 ≥8）。
- **TaskRunner 接口**：业务代码只调 `task_runner.submit(fn, ...)`。**跑通阶段**的实现是 asyncio 后台任务 + PG 状态表，将来换队列不改业务代码。
- **进度推送**：SSE 推送「正在生成 7/12 维度」。用户不必盯着转圈，且任务状态落 PG 使页面刷新可恢复（支撑出题任务的进度可见性）。

### 7.4 供应商健康度反馈路由

EchoMind 把 Agent 的成功率与延迟反馈回 `routing_score()`（P10）。SageMatch 的对应物是**供应商健康度**：

```
每个供应商（LLM / ASR / TTS）维护滑动窗口统计：
  success_rate · p50/p95 latency · 熔断状态 · 连续失败数
        ↓
  health_score = success_rate × w1 + latency_score × w2 × (1 − penalty)
        ↓
LLMGateway / ASRGateway / TTSGateway 路由时按 health_score 加权选择
```

**为什么对 SageMatch 特别重要**：NFR-02 的 1.5s 硬指标直接由 ASR/TTS 首包延迟决定。某 TTS 供应商首包从 300ms 劣化到 900ms 时，系统应自动避开它——**这比人工发现再切配置快得多，也比单纯报错友好**。

**对 EchoMind 的一处修正**：EchoMind 的 `monitor_penalty` 存在 `AgentStats` 的进程内存里。单进程可用，多 worker 时每个进程各算一份、互相看不见。SageMatch **持久化到 `provider_health` 表**，否则扩 worker 后行为不可预期。

### 7.5 评测与质量反馈闭环

EchoMind 的 `EndToEndEvaluator`（P8）结构可整体复用，替换指标集：

| EchoMind | SageMatch | 对应需求 |
|---|---|---|
| `QualityScores`（relevance/accuracy/completeness/helpfulness）+ `overall` | 出题质量四项：**覆盖度 / 重复率 / 干扰项有效性 / 可用率** | FR-A-13、6.1 |
| 意图识别 Accuracy / Macro-F1 / 单类 P-R-F1 | 维度识别的准确率 / 召回率（对标准维度库的标准答案集） | FR-U-01 质量 |
| `_detect_regressions()`：退化 >5% 告警 | **参数调优的前后对比**（FR-A-07 的「可对比」直接复用此机制） | FR-A-07 |
| 基线持久化到 JSON 文件 | 基线落 `eval_runs` 表，支持历史查看 | FR-A-15 |
| `_recommendations()` 输出优化建议 | 「哪个维度质量差 → 建议补物料 / 改 rubric / 调检索参数」 | — |
| — | **新增**：同回答重复评分 N 次的**标准差 σ**（目标 ≤0.5） | 6.2 评分一致性 |
| — | **新增**：多次评分下回答间排序的 **Kendall tau**（目标 ≥90%） | 6.2 排序稳定性 |

EchoMind 用 `temperature=0.0` + 4 维度取均值求稳定；SageMatch 的 σ ≤ 0.5 更严，因此额外需要 §4.4 的**评分四步**。**评测器在 SageMatch 不只是"测质量"，它同时是"验证一致性是否达标"的验收工具**——两者共用一套框架。

**`EvalJudgeAgent` 的职责边界（易被误解的一点）**：它**只算指标，不产出内容**。出题质量评测（FR-A-13）需要"针对给定维度生成题目"，这一步**由编排层复用业务链路的 `QuestionAuthorAgent` + `QuestionCriticAgent`**，`EvalJudgeAgent` 只消费它们的产物并计算 6.1 的四项指标。

这条边界很重要：如果让 `EvalJudgeAgent` 自带出题能力，就会出现**两套出题实现**——一套服务业务、一套服务评测。那样"评测合格"就无法推出"业务合格"，评测的意义被架空。所以评测必须复用同一套生产链路，`EvalJudgeAgent` 只持有**度量类工具**（见 §6.1 的 #4/#5/#8）。

> ⚠️ **v2.7 强化说明：「删除答题板块」与「删除题目集页面」后，这条约束的重要性连续上升了两次。**
>
> 第一次（v2.7，删答题板块）：用户作答这条旁路消失，§7.1 形态一（业务出题链路）成为 6.1 四项指标的**主要参照基准**。
>
> 第二次（v2.9，删题目集页面与维度确认）：**题目在用户端已无任何列表式展示出口**（只在面试中逐题浮现），用户侧彻底没有"看到题目"的渠道。此时形态一成为 6.1 四项指标的**唯一参照基准**——原先"用户看题时的观感"这条旁路也不存在了。**FR-A-13 从"重要验证手段"升为"唯一验证手段"。**
>
> 若允许 `EvalJudgeAgent` 自带一套出题实现，就会形成**自我验证的闭环**：一套实现生成题目、同一套实现给自己算分，指标即使漂亮也说明不了业务链路合格。而且经两轮收缩后，连"用户看题"这个外部的、非评测体系内的旁证都没有了——**闭环将完全封闭**。
>
> 因此**唯一的合法做法不变，且更加不可动摇**：评测复用业务的 `QuestionAuthorAgent` + `QuestionCriticAgent`，`EvalJudgeAgent` 只用度量工具（`blind_test_option` / `check_coverage` / `check_duplicate` / `validate_question` / `rerun_scoring`）。**这也正是出题链路不能被一并删除的根本原因**——它不是评测的可选项，而是评测的前提。

**`EvalJudgeAgent` 的归属澄清**：它是**认知层角色**（§4.1 表 2，因为它用 LLM 做指标判定），但**由编排层在管理端评测链路上调度运行**。§8 需求映射表中 FR-A-13 / FR-A-14 的"保障层"写作「② 认知 + ⑤ 编排」，正是这个分工的体现——指标计算在认知层，链路调度与复用业务出题在编排层。

反馈闭环的落点：评测发现的 rubric 歧义 → 改 `rubrics/*.md` → 热加载 + 版本号变化 → 历史评分记录仍可归因到旧版本。这就是为什么 §4.5 的版本号是必需项，而不是锦上添花。

## 9. 明确不照搬的部分

判断力体现在这里。以下 8 点是 EchoMind 的做法，但 SageMatch 不能沿用：

| # | EchoMind 做法 | 为什么不适用 | SageMatch 改为 | 涉及层 |
|---|---|---|---|---|
| 1 | RAG 只有向量召回 | 技术文档专有名词纯向量会漂移 | 向量 + BM25 + 改写子查询三路 + RRF | ④ 行动 |
| 2 | 用 `AsyncAnthropic` SDK 直连，`tool_use` / `tool_result` 块结构硬编码在 Agent 内 | 违反 FR-A-01/04「两类协议可切换，上层无感」 | 自建适配层，认知层只见内部 canonical 格式 | ④ 行动 |
| 3 | ReAct 循环内可调 LLM（`_rerank`） | 在线 1.5s 预算不允许 | 在线 ReAct 只允许 <50ms 本地数据工具 | ② 认知 |
| 4 | 单层循环（单轮请求-响应） | 面试是 60 分钟连续会话 | 外层会话循环 + 内层 ReAct 两层 | ② 认知 |
| 5 | Skills 热加载无版本号 | 评分可复现需版本锁定 | 内容哈希作 `prompt_version` / `rubric_version` | ② 认知 / ③ 记忆 |
| 6 | 记忆压缩**丢弃**旧消息 | 需要精确引用与完整回放 | 全量存储 + 选择性注入 + 按需取原文 | ③ 记忆 |
| 7 | 无并发控制（客服单请求） | 出题要并行 12+ 维度 | `asyncio.Semaphore` 限流，档位可配 | ⑤ 编排 |
| 8 | `monitor_penalty` 存进程内存 | 多 worker 时互不可见 | 持久化到 `provider_health` 表 | ⑤ 编排 |

另外两处是**设计层面值得改进的**（不是照搬）：
- `_needs_escalation()` 靠关键词扫文本判断升级 → 改为 Agent 输出结构化 `decision` 字段（§4.1）
- `_vote()` 里 LLM 失败时降级到 Embedding/Pattern → 方向正确，但 SageMatch 需在降级时**标记置信度来源**，让用户知道这个维度是「规则猜的」而非模型判断的（§3.1 的 `source_scores`）

**附：本文档与 EchoMind 的关系**

EchoMind 是一个面向客服场景的多 Agent 运行时，本文档仅提取其**可迁移的架构模式**（ReAct 工具循环、路由驱动的多 Agent 编排、角色契约、共享工具 + 白名单、检索优化链路、三层记忆、动态 Skills、LLM-as-Judge 评测、熔断与降级、监控反馈路由，共 10 项），按 SageMatch 的强状态、长会话、硬延迟预算特征做改造，并归位到五层架构中。§9 明确列出了 8 处不照搬之处，避免把客服场景的假设错误带入面试训练场景。
